# PG-29：缺口接收与中断重试幂等

## 范围与依据

- 唯一完整验收阶段：阶段 2。
- 依据：生成规格 §9.5、§10.2、§10.5；执行计划阶段 2。
- 自动化入口：`tests/prd-generator/test_gap_handoff.py`、`tests/prd-generator/run_gap_handoff.py`。
- 本剧本定义检查目标，不记录未经执行的通过结论。CLI 驱动使用人工编写的合成补丁，不调用模型；模型行为试跑必须单独留证，不能以驱动器替代。
- 当前正式生成器尚未实现，缺口由测试辅助函数构造。`prd.md`、追溯和历史版本只作文件归属哨兵，不代表生成结果、有效发布快照或完整生命周期校验；阶段 7 仍须用正式生成器产出的缺口重新联调。

## 合成输入与前置状态

1. 在全新临时工作区，通过公开 `update_analysis` API 或产品 CLI 创建 `GAP-HANDOFF`；项目编号为 `gap-handoff-project`。
2. 初始补丁沿用既有分析测试辅助函数，含 `GOAL-1`、`FR-1` 和无 `gap_request_ref` 的旧问题 `Q-1`。分析修订为 `1`，保留未就绪状态，不假装业务澄清完成。
3. 创建版本化 `prd/gap-requests.json`：计数器为 `2`，`GAPREQ-1` 为本轮目标，`GAPREQ-2` 为不得顺带修改的 `open` 缺口。顶层及目标条目均含应保留的嵌套扩展字段。
4. 以独立分支夹具分别设置目标的完整本需求引用、跨需求引用、空引用和非法引用。跨需求资料通过真实初始更新创建 `EXTERNAL`，但只有显式 `related_analyses` / `--related-analysis` 才授权作为引用校验输入。
5. 保存 `requirement.json` 的 `common` 与 `prd` 块、原始输入、正文、追溯、PRD 事件、历史版本和其他需求的哨兵；后续以原始字节或摘要验证归属。

接收补丁必须保持补丁 `1.0`，以 `change_type: supplement` 的 `operations.add` 向 `questions` 提交候选问题；`value.gap_request_ref` 指向本需求缺口，问题正式编号仍由更新器分配。

## 逐轮操作与人工参考要点

| 分支 | 操作及输入 | 预期可观察结果 |
| --- | --- | --- |
| 本需求引用 | 缺口为 `GAP-HANDOFF/FR-1`，分别提交完整引用及本地 `FR-1` | 保存为 `related_ids: ["FR-1"]`；新接收问题为 `Q-2`，带唯一 `GAPREQ-1` 关联；输入补丁不被 API 改写 |
| 跨需求引用 | 缺口同时含本需求和 `EXTERNAL/FR-1`；先不传资料，再显式提供路径；API 另测分析/来源二元组 | 不传资料即拒绝，即使资料在工作区内也不隐式扫描；显式提供后本需求转本地，跨需求保留完整引用，外部文件不变 |
| 空引用 | 缺口和候选的引用均为空 | 保存空数组，不臆造任何分析条目或旧问题关联 |
| 无效引用 | 完整引用缺需求编号、条目不存在、分隔格式错误，或缺口不存在 | 返回 `fail`、`written=false`，所有业务文件字节不变，不提前占编号或标记交接 |
| 候选与缺口不一致 | 候选遗漏、替换、额外添加或重排缺口的关联 | 逐项核对失败，不能因候选引用本身存在而忽略其与缺口不一致 |
| 重复交接 | 成功接收后重读当前修订，再次 `add` 同一缺口 | 复用 `Q-2`，返回候选别名的 `id_map`；纯重复不推进 revision，不追加 event，不改分析字节 |
| 同补丁重复 | 同一补丁两个候选别名都接收 `GAPREQ-1`，优先级互相不同 | 拒绝整份补丁且业务文件不变，不猜测应采用哪个候选，不建立重复问题 |
| 已有处理进度 | 用公开更新保存 `Q-2` 的 `P1`、`answered` 和实际测试答复，再接收候选 `P2`、`dropped` 和不同答复 | 已有问题全部字段保持；重复候选字段不能覆盖答案、状态、优先级及措辞 |
| 重复加真实增量 | 同补丁含重复接收及另一个普通新问题，或通过 `set` 修改分析字段 | 真实变化仍保存一次新修订；重复接收不占额外问题编号，也不能令整个补丁误判为无操作 |
| 旧修订 | 重放首次接收前的旧补丁 | 即使是重复交接也拒绝；必须重新读取当前分析后生成新补丁，不直接替换旧补丁的修订数字盲重试 |
| 已关闭缺口 | 测试端构造带生成侧 `resolution` 的 `closed` 目标，再重复接收 | 保留关闭状态和依据，不重开、不重写；此分支不声称分析侧完成了缺口关闭 |
| 分析保存失败 | 在真实 `os.replace` 替换目标 `analysis-result.json` 时抛出一次 `OSError` | 返回 `fail`、`written=false`；目标缺口字节不变，仍为 `open`；保留分析 journal，不绕过原有恢复机制 |
| 原事务恢复 | 故障撤去后以旧补丁调用，或以该补丁 `dry-run` | 先恢复 journal 中的分析保存，恰好出现一个接收问题和一次事件；随后旧 base_revision 被拒绝，缺口仍未标记 |
| 恢复后补标记 | 重读恢复后的分析，再生成接收补丁 | 只补 `open -> handed_over`，复用已有编号，不再次保存分析、推进修订或追加事件 |
| 标记中断 | 分析已保存后，在真实 `os.replace` 替换目标 gap 文件时抛出一次 `OSError` | 返回 `fail`，但 `written=true` 且返回已保存 revision；问题存在，gap 原字节仍在，不将失败说成全笔未写 |
| 中断后继续处理并重试 | 先正常保存问题答复和优先级，再重读分析生成接收补丁 | 复用原问题，保留中断后的答复和处理进度；重试仅补标记，不用候选字段覆盖保存结果 |
| 并发生成侧改写 | 在分析结果真实替换完成后、标记前，故障 worker 实际改写缺口文件，保留并发新增 `GAPREQ-3` 和扩展字段；另测只追加换行而 JSON 语义不变 | 检测读时与标记前字节不同，返回 `fail/written=true` 和保存修订；不得只比较解析后的对象，不覆盖并发生成内容；重读后重试仍只补目标状态 |
| 预检 | 对无 pending 的接收补丁运行 `dry-run` | 返回预检结果及候选编号，不保存分析、不标记缺口；已有 pending 事务恢复是明确例外，不假称 dry-run 永远零写入 |
| 关联不可转移 | 对 `Q-2` 用 `update` 将 `gap_request_ref` 改为另一缺口、空值或空串 | 拒绝并保持业务文件不变，不将原接收问题偷偷迁移 |
| 旧格式兼容 | 读取和正常更新无 `gap_request_ref` 的 `Q-1` | 仍然合法，旧问题不被强制添加接收引用，原关联不受新接收污染 |

### 模型行为试跑：独立证据，不由本驱动完成

此部分待实际运行时填写进阶段报告，不把下列预期说成已发生。

1. 给分析 Skill 一个仅含当前分析、合成缺口和允许显式提供的外部资料的全新会话；不给测试参考要点、后续回答脚本或旧黄金输出。
2. 用户首轮：“请接收本需求 PRD 中登记的缺口，继续补充分析；不要替我编答案，也不要直接关闭缺口。”观察模型是否读取缺口、产生 `supplement` 候选并通过正式更新器保存。
3. 若有跨需求资料，下一轮用户明确给出允许读取的分析路径；未给出前不得通过工作区扫描默认为已授权。
4. 重复轮用户：“我再交一次同一缺口，请保留原问题和处理进度。”观察模型是否先重读、复用接收关系而非新建问题。
5. 中断重试轮先由真实脚本故障证据建立“分析已存、标记未完成”的现场，再在新一轮给出重试指令；观察是否重读当前修订并保留已有答复。业务答案如需提供，由实际操作者当轮明确给出并留存，不预写虚构产品确认。
6. 保存真实输入、模型输出、实际补丁、脚本响应和文件变化；模型行为与 CLI/API 协议断言分别报告。阶段 2 的通过结论仍须由执行者根据实际证据判定。

## 文件变化白名单

| 情形 | 允许变化 | 必须保持 |
| --- | --- | --- |
| 新接收成功 | 目标需求 `analysis-result.json`、分析事件；分析写入器原有事务文件和工作区注册表；目标 gap 的 `status` | 缺口其他字段、计数器、其他请求、扩展字段；`requirement.json`、输入、PRD 正文、追溯、PRD 事件、历史版本、其他需求全部文件 |
| 纯重复已标记 | 不允许业务字节变化；互斥锁不计业务内容 | 分析修订、答案、状态、优先级、来源及事件，整个 gap 文件 |
| 新接收 dry-run、无效输入、旧修订 | 不允许业务字节变化；锁不计入 | 分析及 gap 的所有内容；无新的占号或事件 |
| 分析替换中断与恢复 | 分析 journal 及该事务原有分析归属文件，可由后续调用恢复 | gap 必须保持原字节，直到显式成功接收补标记 |
| 保存后标记失败 | 已保存的分析及事件；错误响应要明确 `written=true` 和 revision | gap 未完成标记时不得伪报状态已变，其他生成侧文件不动 |
| 重试只补标记 | 仅目标 `open -> handed_over`；closed 保持 | 分析原字节及事件、非目标 gap 的全部内容 |
| 并发生成侧改写 | 测试并发写入的 gap 字节保留；分析可以已成功保存 | 分析侧不得以旧快照覆盖并发内容，后续重读重试也只改目标状态 |

来源清单、工作区注册表若被既有分析事务以相同字节重写，按字节归属判断不视为业务内容变化；不因此放宽其他需求或生成侧文件的写入权限。
