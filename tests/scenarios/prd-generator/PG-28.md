# PG-28：交错写入时拒绝旧候选并重读

本剧本定义阶段 7 的首次完整验收。依据生成规格 §9.5、§9.10、§12.1 和分析规格 §9.7、§10。用隔离合成需求及安装后的公开脚本；操作者负责安排确定的交错顺序，不能靠睡眠撞时机或只比对报错文字。

## 输入与前置状态

- 从公开分析更新器和正式 PRD 写入器生成合法分析、工作稿和需要时的正式缺口，不静默改写元数据来代替第二个写入方。
- 操作者 A 从公开只读检查取得当前分析修订、PRD 版本或相关状态，保存据此生成的候选；操作者 B 按各分支通过正式入口或真实文件交错点保存新结果。不同分支用隔离工作区，不继承其他分支的冲突。
- 评审参考为 `tests/expected/prd-generator/stage-7.review-draft.md`。分支不要求伪造用户身份、人工业务确认或实际发布。

## 交错分支与可观察结果

| 分支 | 真实操作 | 验证 |
| --- | --- | --- |
| 分析修订变化 | A 取得分析、版本并准备 PRD 候选；B 通过分析正式更新器增加修订；A 仍提交原候选 | 拒绝旧分析修订，不改最后一次合法写入后的业务字节。A 重新读取门禁或同步差异，以新语义和版本制作候选后可成功。 |
| PRD 版本变化 | A 持有合法 PRD 候选；B 通过正式写入器保存另一个合法工作稿版本；A 仍提交原候选 | 拒绝旧 PRD 版本，不覆盖 B 的正文、追溯、计数器、事件或元数据。A 必须读到 B 的改动再制作候选，不只换版本号。 |
| 缺口交接交错 | 从正式 `open` 缺口出发，在读缺口和保存/标记的两个边界之间让另一方写入。验证分析侧先保存问题、随后标记遇冲突，以及生成侧不得把新 `handed_over` 状态当作旧 `open` 覆盖。需要暂停脚本时，仅同步交错点；明确标识实际 CLI 或有钩子的真实程序边界。 | 保留另一方已保存的字节；分析已先落盘时明确记录部分成功，不称全笔零写入。重读后复用同一接收问题，不重复占号，不擦除并发结果，不把 `handed_over` 当作缺口已关闭。 |

## 文件指纹与证据

- 每个分支保留 A 的原始读时值及候选、B 的实际命令或交错点、B 写入后 A 操作前的文件清单和指纹、A 的实际退出码与结果、拒写后同范围指纹、重读及重新提交结果。诊断必须与可观察写入事实一致。
- 先成功保存的业务文件不可被回滚。若分析侧部分成功，只接受已记录、按规格允许的分析写入；生成侧其它业务文件保持。记录失败候选和诊断不等于正式业务文件已写。
- 用真实读操作和重新生成候选证明重读恢复，不把对旧补丁替换数字的重试算作恢复。模拟的冲突响应不作场景证据，也不将脚本测试冒充真实用户试用。
