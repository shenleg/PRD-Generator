# 阶段 6：实际模型输出的人工评审

[打开静态评审页](stage-6-model-review/iteration-1/review.html)。**Outputs** 可查看每组新旧 Skill 的说明、实际工作稿、事件、分析及业务正文差异；**Benchmark** 是客观文件断言，不代表语义或人工已认可。

## 建议按这个顺序核对

1. **有条件稿：能提审，不等于能定稿。** 先看新版第一组的首轮说明和最终事件。应实际保留 `0.1`、进入 `in_review`，没有发布；理由应是分析中的 P1 `Q-1` 业务范围未解决，下一步找产品经理确认、由分析侧更新。不应把「提审」写成评审通过。
2. **就绪稿：先问，再发布。** 查看新版第二组 `model-response.md` 和首轮稿，确认它给出了具体需求、送审稿 `0.1`、分析修订 `1`、拟定稿 `1.0`，并确实停下等待；确认回复是隔离测试驱动在模型实际提问之后提供。对照第二轮说明、实际定稿和事件，检查 `Q-1` 非阻塞研发确认项仍保留，未生成虚假技术结论。
3. **发布后同步：当前稿不等于现行基线。** 查看新版第二组最终稿、业务正文差异和同步说明。最新分析把 `FR-1` 限定为只返回用户选定分组的记录，导出条目 `PRD-FR-002` 不受影响。同步仅生成 `2.0-draft`，不提审、不发布；已发布基线仍为 `1.0`。
4. **旧版对照**：两个旧版都应如实说明阶段 5 没有提审或发布能力，不把只读检查写成已提审，也不绕开工具改状态。未达成的动作不会计分，不等于旧版该拒绝时拒绝错了。

每组每配置只跑一次。程序回归验证了额外的拒绝、篡改、并发及恢复分支；模型未单独走过的分支，不借这两组对话宣称有模型证据。确认本页只表示认可这些隔离试跑和阶段验收范围，不代表真实业务批准、安装、进入下一阶段或 Git 授权。
