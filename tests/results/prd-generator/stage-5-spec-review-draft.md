# 阶段 5：编辑保存与手工修改比较协议补充草案

本文列出阶段 5 实施前发现的缺项及最小建议。**状态：用户已于 2026-11-17 选择“采用整套建议（推荐）”，真实选择见 `stage-5-approval.json`；认可时原文保存在 `stage-5-spec-reviewed.md`，获认可补充已先回写规格，再进入实现。**方案认可不等于最终输出认可或阶段完成。

## 已有依据与缺项

1. 生成规格 §6.3、§8.2 已规定内容修改回交、排版版本递增、`layout_edit`、`manual_edit_detected` 和坚持保留时的不一致标注；事件类型已有，不另造业务事件。
2. §11.3 当前明确 `write_draft.py` 不承担编辑分流。阶段 5 要求实际保存编辑结果，不能未经确认将新职责塞入现有入口，或让只读渲染器/校验器承担业务保存。
3. §6.2、§9.4 只有正文原始字节的 `content_hash`。现有正式工作稿未保证保留可取得的上一正文；摘要不符只能证明发生变化，不能还原旧稿做实际差异比较。运行中的旧字节和完成后清理的事务日志都不是可靠历史正文协议；发布快照也不一定是紧邻的上一工作稿。
4. §9.3 的遗留项定位以分析引用及待设计事项为主，尚未明确“与分析不一致”的 PRD 条目或非编号章节如何稳定定位。现有校验器没有核对这类标注与对应遗留项，也没有据此报告发布阻断。

依执行计划“先改规格”的约束，下面三项需确认后先回写规格，再实施。

## 建议一：复用现有统一写入器

为 `write_draft.py` 增加显式编辑处理模式；默认首稿及 `--sync` 的用途不变。不新增生产脚本，复用现有目录锁、候选校验、原字节并发保护、跨文件保存及前向恢复。

### 编辑行为边界

- **修改请求分流由模型完成**：先比较实际含义。内容变化或无法判断时仅提供分析交接建议，不调用分析写入器，不改 PRD，不把“用户称作排版”作为安全依据。
- **纯排版保存**：仅在完整差异经过语义核对后接纳候选。校验定位标记、正式编号、来源引用和追溯身份没有变化；首次发布前次版本递增，记录既有 `layout_edit`，重新渲染信息并更新正文摘要。脚本结构校验不声称能自动证明自然语言含义相同。
- **手工内容修改检测**：先保留实际旧/新正文及差异。内容变化或无法判断时提示回交分析，显式处理时追加既有 `manual_edit_detected`；未决定前不把当前正文摘要更新为已处理，不覆盖或撤销用户手改内容。只读查看不自动写事件。
- **坚持保留**：实际收到用户回答后才保存对应标注与遗留项，记录检测及处理说明；不借更新摘要解除不一致或冒充已同步。建议将这次带标注的工作稿保存按首次发布前的工作稿规则递增一次次版本；仅检测和追加检测事件不递增版本。此计数细节属于本次待确认建议，不当作现行规格已有结论。
- **分析修订及状态**：先检查待同步状态；编辑不能前移分析基准或代替同步。阶段 5 只接纳未发布工作稿，已发布、废弃及已有发布快照的完整处理仍归阶段 6。
- **读时保护**：编辑输入需绑定读取时的 PRD 版本、分析修订及正文摘要；候选保存前核对实际输入/目标文件，冲突拒写，不能盲改基准数字重试。编辑候选和编号补丁分离，不扩大编号补丁协议。
- **文件归属**：仅更新本需求正文、追溯正文摘要及比较基准、追加事件和必要的 `prd` 元数据。不改 `common`、其他元数据块、分析、缺口身份/交接进度、其他需求或发布快照。编辑中断沿用现有事务，不重复事件。

如用户选择独立编辑入口，以上边界不变，但须在规格 §11.1/§11.3 新增脚本并复用而非复制统一保存机制。

## 建议二：在追溯中保存兼容选填的正文比较基准

建议在 `prd-trace.json` 增加 `meta.content_baseline`：上次经统一保存的 Markdown 原文字符串。它是手工修改比较的旧证据，不是分析权威、第二份可编辑正文或发布快照。

1. 首稿、同输入重复生成、同步及编辑成功保存时，基准与该次正文、`content_hash` 在同一事务内更新。基准以 UTF-8 编码后的原始字节必须与 `content_hash` 一致；保留换行，不做文本归一化。
2. 读取当前正文时先核对 hash；不一致且有有效基准时输出真实差异，覆盖正式条目、非编号章节及未标记文本，不只比较正式条目。渲染器和校验器保持只读，不隐式修复摘要。
3. 旧 `schema_version: "1.0"` 无该字段继续可读、不重编号。旧稿当前正文与 hash 一致时，可在下一次合法统一保存中建立基准；正文已变化但缺基准时，必须明确证据不足。
4. 对缺基准的已改旧稿，可由调用方显式提供旧正文；旧正文 hash 必须匹配既有 `content_hash` 才可用于比较。不依靠猜测、重新生成结果或不匹配的发布快照冒充旧稿。
5. 比较基准不是防恶意篡改认证；适用范围仍是可信本地工作区一致性。代价是追溯多保存一份正文；好处是无需新增业务文件、目录或外部历史服务。

另一种可选方式是每次必须显式提供旧正文而不增加字段，但不保证普通读取时能取得旧稿，也不能自动完成这部分差异判断。若采用该方式，证据不足时保持未处理并要求补资料，不宣称自动检测链路已完整完成。

## 建议三：固定不一致定位与校验语义

复用既有 `【与分析不一致】` 和 `prd:residual` 标记，不新增独立的人工修改清单。

- 对已有正式条目的手工内容修改，在对应条目块内标注；遗留项使用完整 PRD 引用 `需求编号/PRD-FR-001` 等稳定身份定位。
- 对范围等非编号内容，在对应稳定章节内标注；遗留项使用 `需求编号/prd/sections/<section_key>` 定位。此命名仅定位本需求 PRD 已有的内容章节，不允许以信息、变更记录或遗留项章节代替原受影响位置。
- 校验器核对标注与遗留项能对应，目标确实存在，遗留项含差异说明和转回分析的处理建议；正文及遗留项不能只在无关位置出现一次关键词充数。
- 未发布工作稿存在有效不一致标注时，报告具体目标及“不得发布”的警告；标注/遗留项不成对或结构错误为失败。已发布产物含不一致标注则失败。这样保留可沟通工作稿，同时不满足发布所需的 `pass`。
- 排版编辑及同输入重复生成不能抹去既有不一致。分析同步也不能只因 hash 一致、问题状态改变或修订递增就宣称已消除不一致，须核对分析是否真正覆盖对应变化。
- 校验器始终只读；阶段 5 只验证发布阻断依据，不实现或宣称完整 PG-19 发布拒绝已通过。
