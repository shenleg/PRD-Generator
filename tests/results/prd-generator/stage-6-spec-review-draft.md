# 阶段 6：生命周期协议补充草案

本文请用户裁定现有规格未写清的入口、确认和版本规则。**待确认。** 获认可后先更新 `docs/prd-generator/spec.md` 和执行计划，再修改生产代码；本草案不构成发布授权。

## 1. 用两个现有规格内的写入器，明确各自职责

现有生成规格 §9.10、§11.3 只允许 `write_draft.py` 写未发布稿，且只给 `snapshot_release.py` 定义了成功发布的职责。提审、退回、废弃及发布后另建工作稿缺少获认可的入口；事件表也缺少评审退回事件。

- **建议**：`snapshot_release.py` 承接生命周期操作：只读发布检查、提审、退回、正式发布和废弃。只有正式发布操作可以创建快照；其他状态操作仅调整当前稿的状态、信息视图、正文摘要/基准及追加事件，不改业务正文、分析、缺口或版本号。退回复用相同写入规则，新增 `return_review` 事件；旧日志不迁移。废弃要求产品经理明示，停止生成、编辑、同步和发布；仍可只读查看和校验。废弃时保留最后一次发布的快照及其历史基线身份，明确标注需求整体已废弃，不将其当作仍在推进的需求。分析修订落后或未就绪本身不阻止退回或废弃；仍要核对读时状态与文件一致性，不能通过废弃悄悄接纳手改或修复坏文件。
- `write_draft.py` 扩展既有显式同步、编辑入口，在已发布需求上另建或更新工作稿。默认生成仍不覆盖已发布稿，`check_sync.py`、`validate_prd.py`、`render_info.py` 保持只读。需要改变送审稿内容或版本的保存使稿件回到 `draft`，须重新提审；仅只读操作或记录检测事件不改变稿件状态。
- 两入口共用候选校验、写入锁、文件指纹复核和中断恢复。读时保护同时核对版本、状态、分析修订及相关目标原始字节；提审、退回可能不升版本，不能只看版本号。发布快照只能新建，不得替换，发布事务包含两份新快照、定稿后的 `prd.md` 与追溯、`prd` 块和追加事件。原快照、`common`、其他元数据块、缺口及所有分析文件保持不变。继续用既有 `release.snapshots` 作清单，不新增发布业务文件。

## 2. 按当前工作版本递增，而不是反复从旧快照算

§8.2 已规定 `0.N`、首发 `1.0`、发布后内容升主版、排版升次版及后缀，但没有规定下一次变更从哪里起算，也未规定纯分析修订变化怎样编号。下表为建议。主、次分别按整数处理，主版递增时次版清零；正式发布只去后缀（首次发布例外，固定 `1.0`）。改稿时允许工作版本跳过尚未发布的号码，不创建中间快照。

| 起点与操作 | 建议结果 | 仍有效的发布基线 |
| --- | --- | --- |
| `0.5` 提审或由评审退回 | 同为 `0.5`，仅转状态 | 无 |
| `0.5` 满足门禁并获明确确认 | `1.0`，`released` | `1.0` |
| `1.2` 仅排版 | `1.3-draft` | `1.2` |
| `1.2` 同步到有内容性影响的分析修订 | `2.0-draft` | `1.2` |
| `2.0-draft` 再做纯排版 | `2.1-draft` | `1.2` |
| `2.0-draft` 或 `2.1-draft` 再同步实际内容变化 | `3.0-draft` | `1.2` |
| `1.3-draft` 排版后再同步实际内容变化 | `2.0-draft` | `1.2` |
| `1.2` 或 `2.0-draft` 只同步纯修订号变化，内容、依据、遗留、缺口和草稿提示均无实质差异 | 分别为 `1.3-draft` 或 `2.1-draft`；只有实际基准前移才改版，同修订的无变化请求不写 | `1.2` |
| `2.1-draft` 或 `1.3-draft` 提审并获明确确认后发布 | 分别定稿为 `2.1` 或 `1.3` | 切换至该定稿版本，旧快照原样保留 |

纯排版同样走完整提审和发布门禁，不因是排版而自动发布；若需要经用户坚持保存手改不一致标注，这是未批准内容的留痕，不是分析内容同步，按工作稿次版本保存，仍禁止发布。基线来自通过校验的已发布快照而非可编辑的 `prd.md`；当前工作稿和历史基线分开报告。

## 3. 以只读检查和明确确认分开发布

- **提审口径**：保持 §8.3 与 §9.9 的最小交集，只允许当前 `draft`、非待同步、最新分析和 PRD 均为 `pass`，且草稿类型为 `formal_draft` 或 `conditional_draft`。`conditional_draft` 的未答 P1 本身不是 PRD 校验警告；其他独立 `warning` 不算可提审。该口径不把提审门禁误作发布，发布仍必须 `ready_for_document`。
- **确认绑定**：先用只读入口展示具体需求、送审版本、分析修订、检查原因和拟定稿版本。机器给出当前评审状态及内容的指纹（至少覆盖 PRD 元数据、正文、追溯、缺口、已提交评审对应的事件日志和当前权威分析）；只有实际获得产品经理对该版的明示确认，才向发布入口提交该绑定值、`confirmed_by` 和带时区的确认时间。重读全部门禁并复核绑定；任一输入变化（包括同版本退回再提审）则拒写，重新检查和确认。不把初始询问、沉默、检查通过、合成角色或历史同意当成真实确认。CLI 在可信本地工作区校验确认记录及绑定，不提供身份认证。
- **留痕及兼容**：成功发布才追加 `release_confirmed` 和 `release`，二者 `prd_version` 统一用定稿号，前者保留实际确认人和时间、后者登记两份只读快照及其原始字节摘要。新发布必须产出这一对事件；已有阶段 1 合成快照及证据不改字节，不用作正式成功链路。拒绝时逐项报告 §8.4 已知阻断（包括校验可能未单独报出的占位和未关闭的 `handed_over`），无可确认候选或未收到确认不写业务文件。
