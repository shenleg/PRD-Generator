## 3. 发布快照摘要

### 3.1 既有要求

生成规格 §8.5 已规定发布文档与追溯快照并记录摘要，§9.9 规则 11 已要求核验；尚未规定摘要存放位置。

### 3.2 提议字段

既有 `release` 事件保留原字段，增加：

```json
{
  "snapshots": {
    "prd": {
      "path": "versions/prd-1.0.md",
      "sha256": "sha256:<64 lowercase hexadecimal characters>"
    },
    "trace": {
      "path": "versions/prd-trace-1.0.json",
      "sha256": "sha256:<64 lowercase hexadecimal characters>"
    }
  }
}
```

- 上例只是字段示意，不是实际发布记录或可直接通过 Schema 的摘要值。
- 路径相对于当前需求的 `prd/`，并且必须与事件的 `prd_version` 对应，只接受规定的快照文件名；不允许越界、绝对路径或通过符号链接读取外部文件。
- 摘要计算文件原始字节，不对 Markdown 或 JSON 做规范化；修改快照排版也会被检出。
- 同一版本只允许一个 `release` 记录。快照缺记录、记录缺文件、重复发布记录、摘要不符均为失败；没有任何发布时允许 `versions/` 尚不存在。
- `release_confirmed` 事件仍独立记录确认人和时间，发布事件不能代替产品经理的实际确认。
- 不新增发布清单文件；当前工作稿仍由 `requirement.json` 的 `prd` 块描述，历史版本事实保留在不可变快照及追加事件中。
- 这是可信本地工作区的一致性检查，不宣称攻击者同时改文件与日志时仍能认证真伪。

## 4. 编号映射补丁与稳定摘要

### 4.1 提议输入

新增 `schemas/numbering-patch.schema.json`。补丁不沿用分析侧协议，也不提供业务内容写入。

```json
{
  "patch_version": "1.0",
  "requirement_id": "REQ-2026-001",
  "base_prd_version": null,
  "base_analysis_revision": 1,
  "items": [
    {
      "mapping_key": "read-switches",
      "kind": "functional_requirement",
      "analysis_refs": ["REQ-2026-001/FR-1"]
    }
  ]
}
```

- `base_prd_version` 在首次生成且无 `prd` 块时为 `null`，已有工作稿时填读取到的版本。
- `base_analysis_revision` 必须与实际分析修订相符；两项读时版本任一不符就拒绝，不分配编号、不写文件。
- `mapping_key` 是同一需求内稳定、非空的技术映射键，不是正式编号。新映射必填，输出保存为追溯条目的选填扩展字段，重复提交沿用同一键的编号。
- 多个正式条目可以有相同分析引用但使用不同映射键，以支持规格允许的一对多；单次补丁不能重复提交同一键。
- 修改既有映射可以提供 `prd_id`，但必须指向已经分配的条目，且不与映射键冲突；模型不能用它指定一个尚不存在的新正式编号。
- 既有 `1.0` 追溯文件缺少 `mapping_key` 仍可读取；修改这种条目时以明确的既有 `prd_id` 定位。存在歧义时拒绝猜测，不偷偷迁移或重编号。
- 不接受模型提交 `source_digest`、计数器或任意业务正文。编号和摘要由脚本计算，未知写入字段拒绝。
- 旧补丁因版本变化重试时仍拒绝；重新读取后按同一映射键提交才是安全重试，不把旧补丁的版本数字盲改后继续写。
- 本阶段只实现格式与校验；编号实际分配、写入和完整幂等链路属于阶段 3。

### 4.2 明确类别与前缀

| `kind` | 前缀 |
| --- | --- |
| `goal` | `GOAL` |
| `scenario` | `SCN` |
| `functional_requirement` | `FR` |
| `business_rule` | `BR` |
| `constraint` | `CON` |
| `non_functional_requirement` | `NFR` |
| `acceptance_criterion` | `AC` |
| `flow` | `FLOW` |
| `state` | `STATE` |
| `boundary` | `BND` |
| `exception` | `EXC` |

类别对应规格 §6.1 现有分配范围，不扩展到问题、假设、决策、矛盾或缺口。

### 4.3 稳定摘要的唯一算法

- 对每个正式条目，取得全部 `analysis_refs` 对应的完整分析条目对象，按完整引用排序，构造由 `analysis_ref` 和 `item` 组成的对象数组。
- 使用 UTF-8 JSON、对象键排序、紧凑分隔、保留数组顺序、不转义正常 Unicode 字符、拒绝非有限数值，计算 SHA-256 并加 `sha256:` 前缀。
- 使用完整条目对象是为了覆盖标签、来源、关联及其他实际生成字段，防止正文未变却漏掉来源变化；外层文件排版和对象键顺序不参与变化判定。
- 正文 `content_hash` 计算原始文件字节，与上述生成依据摘要分开。
- 当工作稿待同步时，不能仅因旧摘要与当前分析不同就把合法的待同步状态误报为结构错误；应给出待同步警告并列出受影响引用。编号、结构等独立错误仍为失败。

## 5. 缺口文件与分析接收格式

### 5.1 提议封装

```json
{
  "schema_version": "1.0",
  "requirement_id": "REQ-2026-001",
  "counters": { "GAPREQ": 1 },
  "requests": [
    {
      "id": "GAPREQ-1",
      "needed_for": "功能需求",
      "description": "输出表格的行列含义尚未给出",
      "related_analysis_refs": ["REQ-2026-001/FR-3"],
      "raised_in": "0.1",
      "status": "open"
    }
  ]
}
```

- 此为候选示意，不声称已实际登记该业务缺口。
- 继续使用规格已有单条字段；顶层 `requests` 是缺口集合，Schema 同时定义封装与单条结构。
- 高水位计数器不小于历史已分配最大序号；关闭后保留原记录，不删除、不复用编号。没有缺口时为计数器 `0` 和空集合。
- 缺口文件身份必须与当前需求一致，`related_analysis_refs` 使用完整引用，允许空数组；不自动扫描工作区寻找跨需求目标。
- 分析侧仅在接收保存成功后改变相应请求的 `status`，保留顶层计数器、其他请求和未知扩展字段；不改变生成侧补充的关闭依据。

### 5.2 接收问题

- `gap_request_ref` 是分析问题上的选填扩展，值为本需求内的 `GAPREQ-N`，不带跨需求前缀。
- 一个缺口最多对应一个接收问题；问题已回答、暂定或废弃时，重试仍按此引用复用，不新建问题掩盖进度。
- 本需求分析引用填入 `related_ids` 时去掉需求前缀，跨需求保留完整引用；存在性必须核对，空集合不臆造关联。
- `open` 缺口尚无接收问题是合法待处理状态；保存已成功但状态标记中断时，也允许 `open` 缺口已经有一个接收问题，重试继续标记即可。
- `handed_over` 和 `closed` 必须能唯一找到接收问题；缺失或重复是协议错误。
- 本阶段用合成分析夹具检查读取，分析侧生产 Schema、更新器和真实交接实现仍留到阶段 2。

### 5.3 提议关闭依据

为 `closed` 缺口增加必需的 `resolution`；其他状态不依赖该字段判定已解决：

```json
{
  "resolution": {
    "kind": "supplied",
    "analysis_refs": ["REQ-2026-001/AC-3"],
    "reason": "引用分析条目已提供该缺口所需的验收信息"
  }
}
```

- `kind` 为 `supplied` 或 `not_needed`，分别表示已补足或有依据明确不再需要。
- `analysis_refs` 非空，指向当前有效且有内容的分析依据；`not_needed` 必须引用能说明不再需要的分析决策或范围依据，不能只写一句生成器自述。
- 同时检查接收问题已不为 `open`，且正文已无对应占位；暂定依据仍保留【暂定】、验证方式及遗留事项。
- 结构化引用使校验器能检查“确有依据、引用有效、状态相符”，但不能自动证明自然语言内容足以回答缺口。充分性必须按人工参考要点评审，不能只看问题状态或关键词。
- 新字段在关闭时由生成侧维护，分析侧仍只标记 `handed_over`。

## 6. 正文的机器定位

### 6.1 推荐标记

Markdown 的中文标题及布局可以按模板变化，增加不可见 HTML 注释作为脚本定位协议：

- 章节：`<!-- prd:section <key> -->` 与 `<!-- /prd:section -->`。
- 正式条目：`<!-- prd:item PRD-FR-001 -->` 与 `<!-- /prd:item -->`。
- 缺口占位：`<!-- prd:gap GAPREQ-1 -->` 与 `<!-- /prd:gap -->`，标记内容包含“待分析补充”。
- 遗留依据：`<!-- prd:residual <analysis-reference-or-pointer> -->` 与 `<!-- /prd:residual -->`。

标记不增加可见标签。表格内的条目标记放在单元格中，不能破坏表格结构。章节可容纳条目，其他同类块不得嵌套；重复、不成对或交叉标记拒绝。

### 6.2 定位含义

- 章节键使用默认章节的稳定英文名称，例如 `info`、`changes`、`functional_requirements`、`acceptance_criteria`、`residuals`；项目模板可改中文标题，但不丢掉实际内容的键和条目身份。
- 正式编号、标签和状态在对应条目块内核对，不接受在别的章节偶然出现相同文字充数；废止条目仅可在变更记录留痕。
- 缺口占位与未关闭请求一一对应；关闭后原占位消失。相同缺口涉及其他章节时用引用说明，不再登记第二个同编号占位。
- 遗留项使用完整分析条目引用；没有独立编号的待设计数组内容使用分析 JSON Pointer，并按当前分析核对实际内容，不由模型编造编号。
- 文档信息使用脚本渲染的可见键值表，校验可见版本、状态、需求编号及分析修订，不只相信隐藏元数据；不新增第二个权威状态来源。
- 机器定位只提供检查边界。未标注的需求性文字、错误释义和语义漏项仍需人工核对，不把注释齐全等同于整份 PRD 忠实。

## 7. 读取方、校验结果与兼容

| 读取方 | 需要满足的条件 | 本阶段验证方式 |
| --- | --- | --- |
| 分析接收方 | 能取出本需求 `open` 请求、规范化引用、唯一定位已有问题，仅标记请求状态 | 夹具和静态接口检查，不宣称阶段 2 已实现 |
| 编号及同步方 | 稳定映射键、完整引用、确定性摘要、读时版本和历史编号可比较 | 合成补丁及前后追溯夹具，不执行正式分配 |
| 发布与历史读取方 | 能从唯一发布事件找到同版本两份快照，并核对原始字节摘要 | 合成发布事件和快照，不构成实际发布批准 |
| 人工评审方 | 可见文档易读，警告和遗留事项不被隐藏，脚本不越权回答业务问题 | 本次格式评审，未来实际生成另作语义评审 |

- `validate_prd.py` 提议复用现有 `status`、`diagnostics` 和退出码习惯：`pass=0`、`warning=1`、`fail=2`；诊断包含 `rule`、`level`、`item_id`、`path`、`message`。失败优先，保留全部适用诊断。
- 只读读取本需求和调用方显式提供的关联分析，不读 `analysis-report.md`，不调用任何分析写入器，不自行检索工作区。
- 当前工作稿待同步、未处理手工修改和 `open` 缺口按规格给警告；结构、引用、快照和不合法关闭等错误给失败。分析过期仍必须服从规格的草稿类型规则，不能以待同步掩盖错误。
- 没有历史输入时，校验器只能检查当前编号唯一性、高水位等局部条件；不宣称仅靠一份文件证明历史未复用。需要历史不变性检查时，显式提供前一追溯，或使用已登记的发布追溯快照，核对既有编号保留、计数器不回退、引入版本及稳定映射身份不被重置。
- `prd-trace.json` 和缺口封装保留格式版本，允许读取不影响已知字段语义的扩展；未知版本拒绝猜测。分析侧不得因缺口标记而丢掉未知扩展。
- 增加的 `mapping_key` 是选填兼容扩展。当前还没有正式生成器产物，不自动迁移最小消费者的整数版本及简化草稿。
- 本阶段只创建规格已列两份 Schema、另经本提案新增的编号补丁 Schema，以及 `validate_prd.py` 和必要说明；不提前创建 `SKILL.md`、分配器、同步器或发布器。
