# 阶段 2 行为判定清单

本文把已审核的业务参考要点和规格中的机械约束映射到场景，不另造业务参考答案。被测模型不得读取本文件或 `tests/expected/`。实际结果必须由执行记录核对，不能因存在场景文件就标记通过。

## 判定依据

- 第一样例：`high-low-voltage.review.md`，已由用户认可。
- 第二样例：`sample-02-expected.md` 的已审核修订，优先于归档原稿。
- 需求规格第三至六节，以及分阶段执行文档的阶段 2。

| 场景 | 判定要点 | 依据 |
| --- | --- | --- |
| RA-01 | 先复述再列缺口、提问；首轮 1 至 3 个独立核心问题；不把模糊想法当成给过完整原文 | 规格 3、5.2、6.4 |

## 通用产物约束

- [ ] 每个需求单元的 analysis-result.json 与来源清单都通过阶段 1 校验器。
- [ ] 报告具有模板的 13 个章节，标注历史、技术、视觉分析的实际范围。
- [ ] 就绪度按完成清单逐项判断，未满足项关联问题；不能以“问题少”代替完成清单。
- [ ] 技术资料不足不下结论，最多省略技术评估或填 unknown，研发问题保持 ask_dev。
- [ ] 无新增事实覆盖确认内容，推断和假设保留标签。
- [ ] 记录真实提问轮数、无效问题数及判定依据；继续/结束的控制确认与业务问题分开说明，但计入发生提问的总轮数。
- [ ] RA-09 至 RA-11、RA-30、RA-31 的完整回归留在阶段 3，不把预设撤销/更正/新版文档提前执行。
