# 领域知识沉淀

本文件用于分析结束后发现可复用术语、规则或限制，或用户要求沉淀项目知识。执行顺序是**建议 → 具体批准 → 写入**；分析中的确认不等于批准成为项目长期规则。

## 1. 筛选并展示建议

先核对当前分析及实际来源，仅对以下内容提出建议：

| 类型 | 事实确认依据 | 目标类别 |
| --- | --- | --- |
| `term` | 用户已经确认的专业术语 | `domain` |
| `business_rule` | 产品负责人确认的业务规则 | `product` |
| `technical_constraint` | 研发确认的技术限制 | `technical` |

AI推断、暂定假设、未确认事项仅保留在当前需求分析中；需要登记或更新分析时仍使用`update_analysis.py`。技术判断为supported也不自动等于研发确认的长期限制。

每项建议展示：编号、完整正文、适用项目/模块/版本或时间范围、确认事实的依据、来源相对路径及章节、拟写入文件；说明为何值得复用。模拟资料始终显式标注，不能批准成真实业务规范。先限量检查已有知识是否重复或冲突；有冲突交给负责人处理，保留原文件，不用新编号绕过尚未解决的取舍。

完成标准：用户能看见将被保存的准确内容与范围；无法确认资格或适用范围的条目仍停留在建议中。

## 2. 获取具体批准

先明确由当前用户批准，还是由其指定负责人批准。没有机制或没有该条目的明确批准时，不写`knowledge/`。用户结束对话即停在建议；“开始阶段”“采用合成案例”“同意这个流程”都不是具体条目的批准。

当前用户审批时展示单项或带明确编号的批次，使用选择题；记录实际回答原话。批准须绑定完整建议的SHA-256，改正文、范围、项目、来源、合成标识、类型或目标编号后重新展示确认。来源文件在批准后发生变化也须重新核对并批准。

事实确认与沉淀批准分别留痕：`basis`记录前者，`approval`记录后者。不可用模型生成的“用户同意”补足批准，合成测试中的批准记录只能作为程序测试输入。指定负责人时必须先取得用户认可的确认凭据；当前脚本不做账号认证或数字签名。

完成标准：有可对应到准确建议和实际用户决定的批准记录；拒绝或暂缓时无知识写入。

## 3. 通过公开入口写入

生产入口：

```bash
python -I -B scripts/save_knowledge.py \
  --project-root /path/to/workspace/projects/example \
  --proposal /path/to/proposal.json \
  --approval /path/to/approval.json
```

使用与其他生产脚本相同的依赖环境；脚本路径按安装位置指定，不依赖当前目录。项目根必须是既有真实目录，其末级目录名与`project_id`一致。建议和批准文件保存在用户约定的工作文件位置，不直接塞入正式分析JSON、来源清单或`prd/`。

建议JSON（下例仅说明协议，不构成批准或真实业务事实）：

```json
{
  "proposal_version": "1.0",
  "project_id": "example",
  "knowledge_id": "DK-001",
  "category": "domain",
  "kind": "term",
  "content": "【合成示例】采购申请：员工提交的采购请求。",
  "scope": "仅适用于example合成项目，不是实际采购制度。",
  "simulation": true,
  "basis": {
    "status": "confirmed",
    "confirmed_by": "合成案例中的业务角色，非真实负责人",
    "statement": "合成资料声明本例术语已确认。"
  },
  "sources": [
    {"path": "inputs/terms.md", "location": "合成术语", "sha256": "替换为实际来源的64位小写SHA-256"}
  ]
}
```

字段须完整、无多余字段。`knowledge_id`为1至80个ASCII字母/数字/下划线/连字符，首位字母或数字；输出固定为`knowledge/<category>/<knowledge_id>.json`。`scope`非空，`simulation`明确为布尔值；`basis.status`必须为`confirmed`，确认者和原确认说明非空。脚本核对声明形状，不判断其语义真实性，负责人仍需核实角色权限及资料确实支持正文。

来源须为项目根内普通UTF-8文本，路径拒绝越界和符号链接；每项保留章节定位与实际SHA-256。最多64项，每项1MiB、总计2MiB。图片或PDF须先提取文字，保留原始位置，不声称脚本直接解析过它们。

批准文件只含四字段：

```json
{
  "proposal_sha256": "完整建议的规范JSON指纹",
  "decision": "approve",
  "actor": "实际用户或其指定负责人",
  "user_statement": "实际批准原话，不填模型模拟回答"
}
```

建议指纹算法：对解析后的整份建议执行Python `json.dumps(proposal, ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False).encode("utf-8")`，再计算SHA-256。空白/字段顺序不改变指纹，字段内容变化会改变；解析拒绝重复键、NaN和Infinity。

脚本沿用`.analysis.lock`，未完成分析事务时拒绝写入，正常null事务允许；锁和路径检查复用`project_sources.py`。只排他新建一份知识文件，保留建议、批准、指纹与保存时间；不覆盖、删除或合并现有知识，不改源资料、analysis、prd或索引。已有知识要变更时先提出变更建议并请负责人决定；本阶段未实现替换/废止工作流。

CLI输出单一JSON：pass=0、fail=2；仅`status=pass`且`written=true`才表示保存完成。失败可能留下新建但未完整落盘的文件，`file_created=true`如实提示；保留现场、不自动清理、不重试覆盖。该文件不得纳入正式索引，须人工检查。支持Linux/Unix本地遵锁工作区，不保证恶意并发换链防护、跨系统事务或身份认证。

完成标准：实际命令成功、读取输出文件核对正文/范围/来源/批准原样保留，原分析和已有知识字节未被修改。

## 4. 显式纳入检索与后续采用

保存成功后，按用户指定范围将文件列入资料catalog，再使用既有`index_sources.py`和`search_project.py`；见`historical-retrieval.md`。写入脚本不自动索引，不自动赋予current_spec/current_published。合成验收用draft并保留明确合成名称，不进入真实项目资料集。

检索命中仍须读取并核对适用范围、原始来源和确认依据，不把单个需求的规则扩展到所有项目。摘录截断返回warning并不等于没有命中，也不证明已看到完整范围；按命中路径读取必要全文。发现来源变化或新旧冲突时重新核实，不静默覆写知识或历史基线。
