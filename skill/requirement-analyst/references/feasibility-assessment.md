# 有依据的技术可行性评估

在需求涉及现有架构、数据、接口复用、性能、安全或部署限制时读取。本文件定义如何判断与降级；唯一校验器规则9只检查声明自洽，不证明技术事实真实，更不代替研发验证。

## 先限定判断对象

1. 先复述业务预期与已决定的范围。产品尚未决定的权限、输出或验收标准登记ask_product/ask_business，不能改成ask_dev绕过业务阻塞。
2. 把技术问题分成实际需要的能力：当前架构、可复用接口、数据/字段、接口改造、性能与容量、模块影响、权限安全合规、运行/部署/硬件限制、基础设施前提。按需求选择，不机械填十维问卷。
3. 读取用户指定的当前架构/接口/数据字典/代码或实测资料，必要时按historical-retrieval限量检索。每条证据注明source_id、路径/章节或条款、资料类型与有效性；只有按实际读取结果核对过的行号才能引用，不能猜行号，优先使用稳定的章节和条款编号。采用的项目资料保存实际指纹、更新时间与可信依据。
4. 未确认现行有效性、过期草稿和会议设想不能单独证明当前能力。未知更新时间要复核，实际mtime不能补业务确认时间；历史新鲜度与文档内容都要看。多个资料互相矛盾时保留矛盾及ask_dev，不自行挑有利版本。
5. 区分“架构允许扩展”“存在某接口”“接口确已覆盖所需字段、范围与权限”“容量实测达标”。这四者不能互相替代。只确认标识查询，不能推断明细、分页、跨项目授权或导出已存在。

## 五种结论与整体边界

| conclusion | 适用条件 | 必须保留的限制 |
| --- | --- | --- |
| supported | 当前可靠资料直接覆盖本次所需能力、范围与约束 | 仅支持已核实范围，不意味着新容量指标、代码质量或上线验收已通过 |
| conditionally_feasible | 核心数据/架构路径有证据支持，必要改造点及前提明确 | 列明新增/调整接口、适配器、权限回归或容量核验等；未完成的改造不能说成已有能力 |
| risky | 已有具体瓶颈、改造耦合或实测风险信号，现行方案需专项评估 | 说明风险触发依据及影响，不凭空承诺可达指标，不把拟议新方案当现有事实 |
| conflicting | 需求与明确且现行的架构/部署/安全硬约束互斥，且本期不允许改变约束 | 列出两方依据及需确认的变更/替代选项；不由AI擅自放开安全策略或放弃业务要求 |
| unknown | 没有有效资料，或决定本次可行性的核心能力仍无证据 | 部分可复用能力可单独说明，但整体不得靠它抬成supported或conditional |

按需求整体选择结论，不简单按“已有一个接口”或“存在一个风险”套标签。明确硬约束冲突优先如实记录；有可靠风险信号可判risky，但未知性能不等于已经证明风险必然发生。仅知道一小部分能力、核心数据/范围仍未知时用unknown，不用“有条件”包装核心不确定性。

## 输出及证据

使用已有technical_feasibility结构：

- conclusion：上述五种标识之一。
- evidence：逐条content与sources，结论解释应能回到具体资料位置。未知也可保存已知的局部证据，但说明不足以支持整体。
- credibility：说明资料类别、当前有效性、确认/实测范围及限制；写“高”不能代替说明。合成测试明确标为合成，不冒充真实技术负责人确认。
- potential_impact：受影响模块、数据/接口、安全与部署前提，区分已知事实与待验证影响。
- related_questions：本需求中实际存在的ask_dev问题编号，新建可用$别名，不能引用ask_product来凑技术确认。
- risks：未验证项与风险；没有资料时说明缺口，不凭空添加确定的实现、成本、工期、性能上限或架构决策。

所有非unknown结论必须有证据、来源、可信说明和潜在影响。资料不足时明确unknown并登记值得研发确认的能力缺口；不要为了通过校验给空壳证据或把常识当系统现状。

## 就绪度与决策分工

技术结论和文档就绪度是不同维度。业务清楚且技术问题已登记，open ask_dev P1不单独阻止ready_for_document，但草稿必须保留条件/风险，不能写成实现已经完成。产品核心范围未定仍open P0/not_ready，不能因接口存在、结论supported或数据校验pass而抹去。尤其“全部结果”的生命周期、触发时点或完整行集定义会改变核心输出与验收时，对应产品问题是P0，不能因技术资料不足或称作导出边界就降为P1。

确认supported不表示代码已经实现或产品已批准发布。发现conflicting/risky时，要明确当前无法承诺的边界、替代方向及由谁确认；如果这些矛盾使业务方案或核心验收本身未定，登记相应业务问题并按完成清单降级，不将其全部改为研发问题。

## 保存与资料变化

经update_analysis补丁整节设置technical_feasibility；调用同一validate_analysis规则9，不写新技术打分器或第二份校验逻辑。模型负责判断证据是否支撑语义，脚本只核对结构、引用和声明关系。

项目技术资料按history_review采用声明及source-manifest指纹留痕。资料变化先检查实际采用指纹、保留旧来源、新增SRC、保存stale/not_ready并重开受影响问题；实际重新评估technical_feasibility后再以补丁解除stale，避免仅修改结论标签。资料不足也可更新为unknown，不沿用已失效的旧支持结论。

报告第11节展示实际保存结论、证据、来源、影响与研发事项；省略技术节只表示没做评估，不当作无风险。界面体验另按ux-visual-assessment.md，技术资料不证明界面行为；完整技术方案、自动改代码或部署不在本Skill评估范围。
