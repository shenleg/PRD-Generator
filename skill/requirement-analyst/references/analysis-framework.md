# 分析框架

本文件指导首次分析和同次澄清中的业务分析，负责选维度、抽取事实与来源；提问和就绪度分别由另两个参考文件决定。

## 从输入形成当前理解

先复述业务目标、用户、场景、当前诉求和已明确范围；把不知道的内容直接列为缺口，不用行业常见做法冒充原文。

- 想法：只依据用户实际说过的内容，不假设存在完整原文、界面、数据模型或历史规则。
- 存量文档：逐条抽取目标、场景、功能、规则、约束和验收；定位到文件条款、章节、页码或行号。
- 附件：记录来源，提取可识别的页面或规则；不能从截图推断未展示的行为。
- 会议纪要和聊天：结论先待用户确认，不能仅因有人说过就标成业务已确认。

当前理解必须先于本轮问题展示。若资料表述晦涩，展示理解及依据让用户纠正，不默默替用户决定。

## 存量文档检查与拆分

检查缺章、歧义、术语混用、重复条款、多个需求混写及自相矛盾。

1. 按可独立判断范围与验收的需求单元拆分，分别使用需求编号和结果文件，不只把所有事项塞入同一个功能数组。
2. 同一功能的重复或相关条款关联起来；术语是否同指尚未确认时，保留原词和对应问题，不擅自合并业务对象。
3. 原文中的两种冲突说法均保留出处，登记 CNF 并关联实际存在的本需求问题；关联问题 open 时按未处理矛盾判断，不自行选择一边。
4. “按之前规则”“参考现有页面”“和旧报告一致”没有提供资料时，登记缺少什么资料，不能编造其内容。
5. 多需求共用原文时，各自来源清单可以引用同一文档；跨需求的条目关系写“需求编号/条目编号”。

## 按类型选择维度

| 类型 | 优先检查 | 不机械追加 |
| --- | --- | --- |
| 页面交互 | 业务入口、角色、操作流程、状态、异常与验收 | 未要求的视觉样式与完整设计 |
| 规则与组合 | 输入含义、合法状态、组合空间、互斥联动、空输入与输出预期 | 未说明的二进制全排列或联动规则 |
| 数据与接口 | 字段、格式、权限范围、空数据、失败、一致性、验收 | 页面、按钮、登录和语言等常识 |
| 计算与算法 | 输入范围、单位量纲、精度、异常输入、可复现性 | 任意假定规模上限、误差和性能指标 |
| 缺陷修复 | 复现条件、实际与预期行为、影响范围、回归边界 | 新增功能式的收益论证 |

只查与需求有关的维度；多人并发、重复操作和数据一致性在会改变当前结果时检查，不把维度表变成必问清单。

## 价值分析从轻

- 缺陷修复、明确业务约束或原因已经给出，不再问“为什么做”。
- 新增功能原因缺失时，只问一句原因，按 P1 处理；不借机追加频率、成本和收益数字的问卷。
- 原因未知时价值可为 unknown，不擅自否定需求或声称低价值。
- 只记录输入提供的定性、定量依据；不提供数字就不编造收益、节省时间或错误率。

## 推演规则、边界与异常

检查核心流程能否还原、规则是否可执行、状态转换是否存在非法路径；按需要推演空输入、单类输入、重复、规模增长、部分失败、权限、并发与恢复。

推演必须说明“这是候选边界/异常，处理规则待定”，标为 inferred 并引用触发推演的原文。识别到一个场景不代表已经确定了它的处理方式。

涉及排列组合时，即使组合语义和实际规模尚未确认，也要登记条件性的规模增长边界：若组合数量随输入规模增长，生成、展示和选择可能受到影响。不能只写“原文没给性能指标”就跳过该风险，也不能自行假设二态全排列、数量上限或截断策略。

涉及数据导出时，除数量和字段外，分别核对结果生命周期（任务未完成时是否允许导出）、导出内容的访问权限、空结果、大量数据的等待/超时，以及部分失败或数据变化。没有给出处理规则就登记候选边界或问题，不把“全部结果”解释成所有用户均可访问，也不让笼统的研发性能确认替代业务边界检查。

原文明示但含糊的约束仍是 confirmed 的原文陈述；缺少可验收边界另记 GAP/Q。模型建议的解释才是 inferred。例如不能把“尽快上线”擅自转换成日期或硬期限。

## 验收与范围

- 每条核心功能核对前置条件、输入、动作、可判定预期和关键边界。
- “快”“实时”“常用”“友好”不能直接当成可执行验收标准；缺少核心判定方式时登记 P0，不能固定降为 P1。
- 验收草案可用 inferred、to_reassess，但不能拿草案的存在冒充核心验收已完整。
- 本期包含与不包含使用 scope 内的独立通用条目；未提及不等于用户明确排除，空数组也不代表已确认没有范围。
- 术语与领域检查按类型选择；具体单位、精度或数量只能来自输入或明确标注的假设。

## 字段和来源

通用条目使用 id、content、tag、sources、status，具体结构和编号前缀以 schemas 为准。不要用只有正文的字符串替代需要追溯的通用条目。

- confirmed：业务原文明示或用户已明确确认；有矛盾时说明原文陈述，不把其中一方当最终规则。
- inferred：依据输入作出的分析、候选边界或常规默认，不写成业务事实。
- assumption：采用推荐项推进的暂定判断，必须可识别、可验证，关联问题和 ASM。
- 输入和项目资料必须有 source_id，指向 source-manifest.json 中的 SRC 编号；用户回答用 location 标出第几轮，可不另建 SRC。
- 无有效的最后更新时间时清单用 null，不编造日期；资料“存在”不代表其技术内容已经核实。

## 本阶段的分析范围

历史检索与基线对照不开展，在报告说明。技术资料不足时只登记 ask_dev，不给确定结论；可省略 technical_feasibility，并说明没有开展评估。

视觉只判断 ui_dependent；确实涉及界面但缺资料时登记待设计事项，不请求无关的完整视觉稿，也不自行设计页面。核心业务状态的可判定预期仍须澄清，不能因其会显示在页面上就归为视觉细节而跳过。
