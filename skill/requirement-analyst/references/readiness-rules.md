# 完成清单与就绪度

本文件负责每轮保存前的完成清单、问题关联及下游可用程度。分析状态和就绪度独立，数据校验通过不等于需求已就绪。

## 逐项核对完成清单

每个独立需求分别核对，在报告“结论与就绪度”中列出未满足项、原因及对应问题编号。不要根据问题数量或对话轮数猜测完成。

| 项 | 完成条件 | 不满足时 |
| --- | --- | --- |
| 1 | 核心业务目标明确 | 对应 P0 |
| 2 | 核心用户和场景明确 | 对应 P0 |
| 3 | 核心流程可还原 | 对应 P0 |
| 4 | 关键业务规则明确 | 对应 P0 |
| 5 | 没有未处理重大矛盾 | 对应 P0；CNF 关联本需求问题 |
| 6 | 关键边界和异常已分析 | 对应 P0，不能用“已识别但未知如何处理”冒充可执行规则 |
| 7 | 核心验收条件可形成且可验证 | 对应 P0；待重评的草案不算完整 |
| 8 | 历史冲突已处理或明确记录；没对照则说明 | 至少 P1；本阶段说明未对照即可满足声明要求 |
| 9 | 技术风险有结论或研发确认项 | 至少 P1；登记适当 ask_dev 即可满足，不要求编造技术结论 |
| 10 | 已判断是否依赖界面 | 至少 P1；本阶段只作判断和必要的缺资料记录 |
| 11 | 剩余风险和假设记录清楚，不阻碍当前草稿形成 | 至少 P1，明确谁如何验证假设 |

任一项不满足，都必须关联问题；没有问题视为分析遗漏，先补问题再保存。

第 1 至 7 项仍不满足，就绪度为 not_ready；第 8 至 11 项不满足，不高于 conditionally_ready。只登记了问题并不一定解决了业务缺口；尤其不能把“能写一条验收草案”当成“已有可判定结果”。

## 问题与就绪度的联动

依次判断：

1. 有 open P0、未处理重大矛盾，或核心完成清单仍不满足：not_ready。
2. 核心已可表达，仍有 open 且无有效假设的产品/业务 P1：conditionally_ready。
3. 完成清单满足，产品/业务 P1 已回答或有有效暂定假设：ready_for_document。

- active 或 to_reassess 的 CNF 所关联问题 open 时仍是未处理矛盾；withdrawn 的旧矛盾不单独阻塞。
- 只有 active 的 ASM 或 DEC 才能支撑当前问题状态，撤销或待重评记录不能代替有效结论。
- ask_dev 的待确认事项不单独阻塞文档就绪，必须保留给研发；缺少需求本身的可判定预期仍是产品 P0，不能改成 ask_dev 来回避阻塞。
- lookup 缺资料不等于已评估无风险；是否阻塞取决于资料缺失是否使核心规则、验收仍不可确定。
- 用户接受风险或采用假设之后，也要重新检查核心清单；仍无法表达核心预期就仍为 not_ready，不靠关闭问题强行抬高就绪度。

## 分析状态

- analyzing：本轮正在分析。
- clarifying：已有值得等待用户回答的问题。
- paused：用户明确暂停。
- completed：本轮已收敛或用户要求结束；可以同时是 not_ready。
- stale：已有资料变化，结果待重评；新版文档先保存过期状态，完成受影响项重评后再更新。

状态、就绪度和修订号仅以 analysis-result.json 的 meta 为权威，报告展示读取值，不独立维护另一份状态。

## 保存前校验

1. 按 incremental-update.md 产出补丁，每轮填写十一项 completion_checks；已有对象引用正式编号，新对象使用临时别名，标签和来源沿用 schemas。
2. 调用 scripts/update_analysis.py；它对应用后的候选调用唯一的 validate_analysis.py，检查结构、完成清单及规格 9.6 的关系规则。
3. 诊断 fail 时按条目与原因修正补丁，最多 3 次；正式结果保持上次合法值，仍失败则说明问题，不宣称本轮已完成。
4. 从脚本实际保存的 analysis-result.json 整理报告；warning 要显式提示并保留过期使用限制，dry-run 不算保存成功。
5. 校验器不检查自然语言业务充分性，不能用它代替前面的完成清单与行为核对。

## 下游限制

| 结果 | 使用限制 |
| --- | --- |
| 校验 fail | 不得交付下游 |
| stale / warning | 提醒先重新评估；坚持使用只能标注基于过期分析 |
| not_ready | 只能生成标注风险的初步草稿 |
| conditionally_ready | 草稿醒目列出遗留问题、假设、研发确认项 |
| ready_for_document | 可形成正式 PRD 草稿，但不等于研发全部确认或产品批准发布 |

报告同时注明未开展的历史、技术、视觉分析及其原因；不得把缺省节或空数组解释成“已经评估，无问题”。
