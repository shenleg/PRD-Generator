# 提问与结束策略

本文件负责问题排序、每轮问法、回答状态及结束条件；问题是否导致未就绪由 readiness-rules.md 判断。

## 先登记，再决定本轮问什么

所有重要缺口进入 questions，但不要求一次问完。按核心错误或无法验收的影响排序，前置决策先于依赖它的细节。登记与当轮提问是不同动作。

首轮先解决可能造成非授权操作、数据丢失或输出不完整的最终业务规则，包括未提供的既有处理规则。术语关系若不妨碍用户针对同一个操作直接说明权限和处理方式，应保留原词并登记术语问题，不让命名确认挤掉这些操作决策；若对象确实不同而无法回答，再优先说明对象关系为何构成阻塞。不能因为登记了一串 P0 就忽略其影响轻重。

| 优先级 | 判断 | 处理 |
| --- | --- | --- |
| P0 | 不明确会导致核心业务错误、无法还原关键流程或无法验收 | 优先澄清，或在结束时如实保留风险 |
| P1 | 影响重要功能、体验或实现，但核心需求可表达 | 按价值选择提问，未确定时可采用有依据的推荐作为假设 |
| P2 | 常规细节 | 标 inferred，不主动提问 |
| P3 | 非本期必要的优化 | 记建议，不打断用户 |

优先级随上下文判断，不固定按问题名分级。复现预期、筛选条件或字段若影响独立需求的核心验收就是 P0，不因常见而自动当 P1。

## 解决途径与问题责任方

- ask_product / ask_business：业务范围、权限、输入输出、可判定预期和验收标准。
- ask_dev：当前能力、数据模型、接口、更新机制、技术限制。登记给研发，不抛给产品作实现承诺。
- ask_design：已确定业务之后确需设计决策的事项；本阶段不展开完整视觉分析。
- lookup：用户提及但未提供的明确资料；登记缺失，不臆造内容，也不运行历史检索。
- infer：可由常规默认形成的推断，不占用主动追问额度。

业务“实时”的可接受延迟与当前轮询/推送机制是两个问题，分别向产品和研发登记。一个问题只解决一个核心决策，通知对象、渠道、触发时机不能打包成一个选择题。

## 每轮提问

1. 先展示当前理解，再说明缺口及为何值得问。
2. 本轮只提出 1 至 3 个独立问题；没有值得问的问题时不凑数。
3. 每个问题给 2 至 4 个有效选项，另加“其他”“暂不确定”，标明推荐项与理由。
4. 推荐项可以是讨论起点，用户未采用前不是已确认规则或已采用假设。
5. 只把本轮真正向用户提出的问题计入追问；研发登记、未来问题列表不能伪装成要求产品当轮回答。
6. 已确认、已回答或已有有效暂定假设的相同问题不重复问；新答案导致新边界时，明确它为何是新问题。
7. 新增功能原因缺失最多问一句原因；缺陷、明确约束和原因已知时不问价值，不索要 ROI 数据。

## 六种状态及关联记录

| 状态 | 使用条件 | 必要记录 |
| --- | --- | --- |
| open | 还没有回答或实际处理结论 | 保留原因、影响和关联编号 |
| answered | 用户明确回答 | answer 及相关条目的 user_answer 来源 |
| provisional | 用户选“暂不确定”，采用上一轮推荐继续 | active ASM、basis、verification（验证人和途径）、related_question |
| risk_accepted | 用户明确接受仍不明确的风险 | 明示接受的回答及来源，不能由分析者代为接受 |
| excluded | 用户明确本期不支持 | active DEC，确认人/时间/related_question，以及独立 out_of_scope 条目 |
| dropped | 问题已经不成立 | 保留旧问题及原因；不得仅为消除阻塞而使用 |

采用假设后，相应业务内容须保留 assumption 标签；不能把问题改为 answered，也不能把推荐语写成用户已确认。决策确认人使用真实可识别身份或“用户”，确认时间记录本次实际发生确认的时间；不编造具体姓名或倒填历史确认时刻。

“未回答”和选择“暂不确定”不是一回事。用户要求停止或达到上限时，未回答 P0 仍保持 open，不能批量转假设或接受风险。

## 结束与上限

默认业务追问上限为 5 轮，调用方可以明确配置。每次真正发出问题的轮次都要记录；到上限的继续/结束控制确认单独注明，不把它当成额外一批业务追问。

- 用户明确结束：立即停止所有新问题，保存当前结果。open P0 保持 open，analysis_status 为 completed，就绪度按完成清单判断，报告醒目标出风险。
- 达到上限：剩余可合理推荐的产品 P1 按推荐项登记暂定假设，并写验证人和途径；仍有 open P0 时只问继续还是结束。
- 技术能力或缺失资料不能靠轮数变成事实；待研发事项和未取得的资料如实保留，不假装已经核实。
- 用户明确继续：保留已问轮数，按此次授权的后续轮次继续；用户选择结束后不追加业务问题。
- 暂停：保存当前数据，analysis_status 为 paused，不把暂停当成风险接受或业务完成。

同次澄清可以吸收答案并更新整份结果；更正、撤销和新版文档的专门增量机制在后续阶段实现，本阶段不假装已调用补丁脚本。
