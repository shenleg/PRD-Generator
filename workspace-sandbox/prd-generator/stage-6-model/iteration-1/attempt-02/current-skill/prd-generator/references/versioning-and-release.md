# 评审、发布、废弃与基线

本参考适用于提审、退回、发布、查看基线、废弃，以及发布后的同步或排版。评审是送给产品经理，不等于认可；发布必须有对具体送审稿的明示确认。

## 明确操作，再检查

| 用户意图 | 采取的操作 |
| --- | --- |
| 看能否发布／查看基线 | 只读 `snapshot_release.py DIR check`，说明阻断或现行快照；不写文件。 |
| 提交评审 | `check --for-action submit-review` 通过后，用原绑定值执行 `submit-review`。只能从校验通过、未待同步的 `formal_draft` 或 `conditional_draft` 提审；状态改 `in_review`，版本不变。 |
| 评审退回 | `check --for-action return-review` 后执行 `return-review`。原 `in_review` 改回 `draft`，记录 `return_review`；再次发布需重新提审。 |
| 产品经理要求发布 | 先只读检查。将需求、送审版本、分析修订、拟定稿版本展示给产品经理，取得对这一份稿件的明示确认后才执行发布。 |
| 产品经理明示整体废弃 | `check --for-action deprecate` 后提交真实明示确认。保留全部文件；停止生成、编辑、同步和发布，仍可只读查历史。全撤销只提示，不能代做废弃决定。 |

所有写动作使用同一操作的检查结果 `--binding`。绑定变化时重读，发布或废弃需重新确认。命令与恢复参数见[脚本说明](../scripts/README.md#评审发布和废弃)。

## 发布门禁

逐项解释已知阻断，定位条目、版本或缺口，不只报第一项：

1. 最新分析校验为 `pass`，未过期。
2. 就绪度为 `ready_for_document`；有条件稿可评审，但发布前要解决影响就绪的事项。非阻塞研发确认项保留在遗留事项中，不伪造技术结论，也不单独阻断发布。
3. PRD 基于最新分析修订，未待同步。
4. PRD 校验为 `pass`，无占位、未关闭缺口或【与分析不一致】。`handed_over` 或接收问题状态改变都不能代替内容补足。发现手改先按[修改分流](numbering-and-trace.md)处理，不能刷新摘要来绕过。
5. 当前状态是 `in_review`，存在对应的提审记录。
6. 实际收到产品经理对刚刚展示的版本的明确确认，有可记录的姓名及带时区的实际确认时间。初始请求、询问能否发布、沉默、校验通过和历史同意都不构成这次确认；不从 Git 用户、工作区名或模型自身推断确认人。

确认后执行 `release --binding … --confirmed-by … --confirmed-at …`。脚本重新检查门禁、版本、对应评审和绑定；不为兼容旧确认改数字重试。只有返回 `applied: true` 才报告已发布。发布后检验两份快照和摘要，成功与临时文件、拒绝、未完成事务分开报告。这里的发布是在工作区创建 PRD 基线，不公开上传或部署。

## 工作稿版本与基线

- 首次草稿 `0.1`，首次发布前保存递增次版，首次发布为 `1.0`。提审、退回、仅记录手改检测及废弃不改版本。
- 发布后以当前工作版本递增：实际内容或依据变化经同步升主版、次版归零；纯排版、只前移分析修订或按规则保留手改不一致升次版。产生或更新工作稿一律回到 `draft` 并带 `-draft`，如 `1.0` → `2.0-draft` → `2.1-draft` → `3.0-draft`。排版也要另走提审和发布，成功发布才去掉后缀。
- 当前稿不等于基线。以 `release` 事件与两份快照原始字节校验通过的最新定稿为准；查看时说明当前稿和基线各自的版本。旧快照是只读、不可覆盖的；不能从当前 `prd.md` 重做快照或刷新已发布摘要。已废弃需求的最后定稿作为历史参考，不称为待推进的需求。
