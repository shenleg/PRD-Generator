# 内容、状态和遗留事项

只从经校验的分析生成需求内容。确认内容直接陈述；`inferred` 逐条标【推断】并汇总待验证内容；`assumption` 标【暂定】，列出对应假设、依据和验证方式。`to_reassess` 另标【待确认】，不得写成确定事实。不同确定性的内容拆开，避免标注范围不明。`withdrawn` 不进入有效章节；已有正式编号仅在变更记录留痕、不复用。`excluded` 问题及其决策放入本期不含，不当作需求。

遗留事项必有，并分别以完整分析引用定位：所有 `open` 的 P0/P1 问题及解决途径和推荐项；`provisional` 问题及对应假设、依据和验证方法；`risk_accepted` 问题及对应决策；未答的 `ask_dev`；待设计事项；未处理矛盾、缺口；推断内容。`formal_draft` 也必须保留暂定假设和研发确认项，不自行修改分析优先级、解决途径或就绪度。无独立编号的设计事项用 `/ux_assessment/design_pending_items/<index>` 定位。

模板或写作所必需的信息确实缺失时，在对应位置写“待分析补充”，逐项登记 `gap-requests.json` 并列入遗留事项；不要臆造事实。完整引用用 `需求编号/分析条目编号`，无关联时用空数组。缺口按规格 §9.5 使用独立递增 `GAPREQ-N`，保留计数器和历史状态；每个未关闭请求只对应一个占位，其他位置引用该缺口。建议用户交回需求分析，不写分析文件；`handed_over` 不代表解决。空必有章节本身只写“分析结果中无此项”，不能仅据此自动登记缺口。
