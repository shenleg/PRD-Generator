# 文档说明

本文档描述 PRD Generator（需求文档生成 Skill）的完整形态：做什么、不做什么、怎么读取分析结果、怎么生成和维护 PRD、怎么同步和发布、产出什么。

它是 Requirement Analyst（需求分析 Skill）的配套文档。两份文档的术语、编号、数据格式和协作规则必须一致，分析侧的规则以《Requirement Analyst 规格说明书》为准。

- 本文档**不划分版本，也不含实施顺序**。实施分期由使用者根据本文档另行制定。
- 能力之间的依赖，用“前提资料”和“降级规则”表述，见 4.4。
- 规范用语：**必须**表示成品必须满足，**应当**表示强烈建议，**可以**表示可选。
- 命名约定：正文用中文；文件名、目录名、数据字段名、枚举值、编号前缀等标识符用英文，写在反引号中；通行术语（Skill、PRD、JSON、Schema 等）保持英文。

# 一、定位与目标

## 1.1 产品定位

核心问题：**需求已经想清楚了，怎样写成一份准确、可追溯、可维护的 PRD？**

本 Skill 读取 Requirement Analyst 产出的结构化分析结果，生成标准 PRD，并负责 PRD 的正式编号、变更同步、版本管理和发布。它是“写清楚”的一端，不重新分析需求。

## 1.2 协作方式

- 分析结果支撑得了的，准确写出。
- 分析结果没有的，不补全为事实，回交给分析。
- 分析中标为推断、假设的，在 PRD 中保留标注。
- 需求在分析侧发生变化时，只同步受影响的部分，编号保持稳定。
- 用户只想改措辞和排版的，直接改好，不惊动分析。

## 1.3 核心目标

让 PRD 与分析结果始终一致，每条内容都能追溯到分析条目，每次变化都可见、可审、可回退。

## 1.4 要解决的问题

1. 需求想清楚了，落成 PRD 时标注丢失，推断和假设被写成既定事实。
2. PRD 与分析结果各改各的，逐渐不一致。
3. 需求变化后 PRD 不同步；或同步时整篇重写，编号和引用混乱。
4. 已撤销的需求仍留在 PRD 中。
5. 遗留问题、暂定假设、研发确认项分散，PRD 读者看不到风险。
6. 生成 PRD 时遇到分析缺口，自行补全。
7. 发布缺少明确条件和确认记录，草稿被当成基线。
8. 已发布的版本被悄悄修改，无法追溯。

## 1.5 最有价值的五种能力

1. **忠实**：只写分析结果支撑的内容。
2. **保留不确定性**：该标注的标注，该列为遗留的列出。
3. **可追溯**：每条正式需求都能回到分析条目。
4. **会同步**：分析变了，只改受影响的部分，编号不变。
5. **守基线**：已发布版本不可变，发布有条件、有确认。

## 1.6 使用者与上下游

- **使用者**：产品经理（生成、评审、发布）、研发和测试工程师（查阅 PRD 及其遗留事项）。
- **上游**：Requirement Analyst，是本 Skill 的前置 Skill，协作规则见第十节。
- **下游**：已发布的 PRD 成为项目的现行需求基线，同时是 Requirement Analyst 的历史需求资料。

# 二、职责边界

## 2.1 本 Skill 负责

把需求**写清楚**：

- 检查并读取分析结果，按就绪度决定生成方式。
- 生成 PRD 草稿。
- 正式需求编号与引用，以及与分析条目的追溯关系。
- 保留推断、假设、待确认的标注，汇总遗留事项。
- 分析结果更新后的同步。
- 仅涉及措辞和排版的修改。
- PRD 的版本管理、评审状态和正式发布。
- 把生成中发现的分析缺口回交给分析。

## 2.2 Requirement Analyst 负责

把需求**想清楚**：理解、分析、追问、收敛、变更影响，创建需求目录并分配需求编号，维护 `analysis/` 下的全部文件。

## 2.3 明确不做

- 不补全、不修改、不推翻分析内容，不写入 `analysis/` 下的任何文件。
- 不做新的业务分析、价值判断和技术可行性评估。
- 不裁决矛盾，不代替产品经理确认需求、风险或发布。
- 不直接修改已发布版本。
- 不创建需求目录，不分配需求编号。
- 不负责高保真 UI 设计稿和技术设计文档。

# 三、基本原则

1. **分析结果是唯一依据**：PRD 的需求性内容都必须来自分析结果。
2. **忠实表达**：不增减需求含义，不借润色引入新规则。
3. **保留标注语义**：推断、假设、待确认不得写成确定内容。
4. **状态决定去留**：已撤销的不进入 PRD，待重评的不写成确定内容。
5. **缺口回交，不自行补全**：PRD 需要而分析没有的内容，登记为缺口。
6. **编号稳定**：正式编号一经分配不变、不复用、不重排。
7. **同步最小化**：只重写受影响的条目，未变的内容一字不动。
8. **发布必须确认**：草稿不是基线；发布须产品经理明示，不得代为确认。
9. **已发布不可变**：修改只能产生新版本。
10. **修改分流**：内容性修改回到分析，排版性修改直接处理。
11. **少打扰用户**：只在缺口、门禁不满足和发布确认时才向用户提问。

# 四、输入与工作方式

## 4.1 输入

| 输入 | 来源 | 处理方式 |
| --- | --- | --- |
| `analysis/analysis-result.json` | Requirement Analyst | 唯一权威输入，读取前必须校验 |
| `requirement.json` | 工作区 | 读 `common` 块，读写 `prd` 块 |
| `prd/` 下已有文件 | 本 Skill | 同步和版本管理的基础 |
| 用户的生成、修改、评审、发布指令 | 对话 | 按 4.3 分流 |
| 项目 PRD 模板（可选） | 用户指定 | 按模板组织章节，见 5.2 |
| `analysis-events.jsonl`、`source-manifest.json` | 分析侧 | 只读，仅用于补充变更原因和来源名称，见 4.4 |

## 4.2 生成前检查

每次生成或同步之前，必须先做以下检查：

1. 需求目录下有没有 `analysis-result.json`。
2. 调用分析侧的 `validate_analysis.py` 校验。
3. 读取 `meta.analysis_status` 和 `meta.readiness`，决定草稿类型 `draft_kind`。

| 检查结果 | 草稿类型 | 处理 |
| --- | --- | --- |
| 没有分析结果 | 无 | 不生成，转入需求分析 |
| 校验失败 | 无 | 拒绝生成，说明出错条目，转回需求分析修正 |
| 校验警告：分析已过期 | `stale_draft` | 提示先重新评估；用户坚持时，只生成明确标注“基于过期分析”的草稿 |
| `not_ready` | `risk_draft` | 只生成标注风险的初步草稿 |
| `conditionally_ready` | `conditional_draft` | 可以生成，遗留事项必须醒目列出 |
| `ready_for_document` | `formal_draft` | 可以生成正式 PRD 草稿，仍须产品经理后续确认 |

分析已过期的优先级高于就绪度。其他校验警告必须向用户提示。

## 4.3 工作方式

| 方式 | 触发 | 说明 |
| --- | --- | --- |
| 首次生成 | 用户要求生成 PRD，且 `prd/` 为空 | 按 4.2 检查，生成，分配正式编号，建立追溯 |
| 同步 | 分析修订号高于 PRD 基于的修订号 | 见第七节 |
| 排版修改 | 用户只改措辞、格式、排版 | 直接处理，见 6.3 |
| 内容修改 | 用户要改需求内容 | 转回需求分析，见 6.3 |
| 评审 | 提交产品经理评审 | 见第八节 |
| 发布 | 产品经理要求发布 | 见第八节 |
| 废弃 | 需求整体不再做 | 产品经理明示后标为已废弃，保留全部文件 |

## 4.4 能力前提与降级

资料不具备时，对应能力必须降级，不得因缺资料而中止，也不得臆造。降级的内容必须写入“文档信息”的“未覆盖的分析项”。

| 能力 | 前提资料 | 资料缺失时的降级 |
| --- | --- | --- |
| 门禁检查、基础章节、标注保留、编号与追溯、遗留事项汇总、同步、版本与发布 | 分析结果的必填节 | 无需降级 |
| 背景与价值章节 | `value_assessment` 已填 | 缺省则不生成该章节，不写“无明确收益” |
| 技术说明章节 | `technical_feasibility` 已填 | 缺省则不写技术结论，只列 `ask_dev` 类研发确认项 |
| 界面与交互章节 | `ux_assessment.ui_dependent` 为 `true` | 为 `false` 则不生成；为 `true` 但缺视觉资料，列为待设计事项，不假设界面 |
| 关联与影响章节 | `impact_analysis` 已填 | 缺省则不生成，注明“分析结果未包含历史需求对照” |
| 验收条件挂靠功能需求 | 验收条件带 `related_ids` | 缺省则验收条件独立成节，不自行推断挂靠 |
| 变更原因说明 | 可读取 `analysis-events.jsonl` | 无法读取则只按条目比对生成变更摘要 |
| 来源名称显示 | 可读取 `source-manifest.json` | 无法读取则只显示 `source_id` |
| 项目 PRD 模板 | 用户指定 | 缺省使用 5.2 的默认章节 |

# 五、生成能力

## 5.1 能力总览

九个模块。

| 编号 | 模块 | 核心问题 | 主要输出 | 前提资料 |
| --- | --- | --- | --- | --- |
| 01 | 门禁检查 | 现在能不能生成，生成成什么样 | 草稿类型或拒绝理由 | 分析结果 |
| 02 | 内容映射 | 分析条目写到 PRD 的哪里 | PRD 章节内容 | 分析结果必填节 |
| 03 | 标注保留 | 哪些内容不是既定事实 | 推断、暂定、待确认标注 | 分析结果 |
| 04 | 编号与追溯 | 正式需求怎么编号，对应哪些分析条目 | 正式编号、`prd-trace.json` | 分析结果 |
| 05 | 遗留事项汇总 | 读者必须知道哪些风险 | 遗留事项章节 | 分析结果 |
| 06 | 缺口回交 | 分析里没有的内容怎么办 | `gap-requests.json` | 分析结果 |
| 07 | 同步 | 分析变了怎么跟 | 更新后的 PRD、变更摘要 | 已有 PRD、分析结果 |
| 08 | 修改分流 | 这个修改由谁处理 | 转回分析或直接处理 | 用户指令 |
| 09 | 版本与发布 | 什么时候算正式，怎么留痕 | 版本快照、发布记录 | 已有 PRD |

## 5.2 PRD 章节结构

默认章节如下，顺序固定，便于前后比对。

| PRD 章节 | 来源 | 必有 |
| --- | --- | --- |
| 文档信息 | `requirement.json`、`meta`、`context` | 是 |
| 变更记录 | `prd-events.jsonl` | 是 |
| 背景与价值 | `value_assessment` | 否 |
| 目标与范围 | `requirements.goals`、`requirements.scope` | 是 |
| 用户与场景 | `requirements.scenarios` | 是 |
| 功能需求 | `requirements.functional_requirements` | 是 |
| 业务规则 | `requirements.business_rules` | 是 |
| 流程与状态 | `business_assessment.flows`、`states` | 否 |
| 边界与异常 | `business_assessment.boundaries`、`exceptions` | 是 |
| 约束与非功能需求 | `requirements.constraints`、`non_functional_requirements` | 否 |
| 验收条件 | `requirements.acceptance_criteria` | 是 |
| 界面与交互 | `ux_assessment` | 否 |
| 技术说明与研发确认项 | `technical_feasibility`、`questions`（`ask_dev`） | 否 |
| 关联与影响 | `impact_analysis` | 否 |
| 遗留事项 | `questions`、`assumptions`、`gaps`、`conflicts`、`decisions` | 是 |
| 附录 | `context.domain_terms`、来源 `source_id` | 是 |

- 必有章节没有内容时，写“分析结果中无此项”。
- 非必有章节在分析结果中缺省时，不生成该章节，并在“文档信息”的“未覆盖的分析项”中列出。**缺省不代表不存在问题**，只代表没有做这项分析。
- 用户指定项目模板时，章节按模板组织，映射、标注、编号规则不变；模板要求而分析结果没有的内容，按 5.6 回交。

## 5.3 标注保留

| 分析 `tag` | PRD 写法 |
| --- | --- |
| `confirmed` | 直接陈述 |
| `inferred` | 条目末尾标注【推断】，并在遗留事项的“待验证内容”中汇总 |
| `assumption` | 条目末尾标注【暂定】，关联的 `ASM-` 条目列入遗留事项，写明依据和验证方式 |

- 状态为 `to_reassess` 的条目标注【待确认】。
- 不得把带标注的内容写成确定语气；不得把已确认和推断的内容并入同一句，使标注无法落到具体内容上，应当拆开写。

## 5.4 状态决定去留

| 分析 `status` | PRD 处理 | 追溯状态 |
| --- | --- | --- |
| `active` | 正常写入 | `active` |
| `to_reassess` | 写入并标注【待确认】，不得写成确定内容 | `to_confirm` |
| `withdrawn` | 不进入有效章节；此前已有正式编号的，在变更记录中保留一行，编号不复用 | `abolished` |

分析中已排除的内容（`excluded` 问题及其决策）写入范围的“本期不含”，不作为需求。

## 5.5 遗留事项汇总

遗留事项是 PRD 的必有章节，必须汇总以下内容，且与分析结果一致：

1. `open` 状态的 P 0、P 1 问题，含解决途径和推荐项。
2. `provisional` 状态的问题及对应假设，含依据和验证方式。
3. `risk_accepted` 状态的问题及对应决策。
4. 研发确认项：解决途径为 `ask_dev` 且未回答的问题。
5. 待设计事项：`ux_assessment.design_pending_items`。
6. 未处理的矛盾和缺口。
7. 带【推断】的内容汇总。

草稿类型为 `formal_draft` 时，仍须列出暂定假设和研发确认项：**已就绪不代表研发已确认所有技术细节**。非阻塞研发确认项按分析侧规格 §6.7 判定，可以保持 `open`；本 Skill 不自行修改问题优先级、解决途径或就绪度。

## 5.6 缺口回交

触发：模板章节或写作所必需的信息，分析结果中没有。例如某个功能点没有对应验收条件、没有范围声明、术语没有定义。

1. 不补全为事实，不用常识推断充数。
2. 在对应位置写“待分析补充”占位，并在 `gap-requests.json` 登记。
3. 告知用户，建议转入需求分析；分析 Skill 在“补充”时按 9.5 登记接收问题并保留缺口引用，重复交接时复用已有问题。
4. 下一次同步时，通过该引用检查分析结果；仅在满足 9.5 的关闭条件后，关闭缺口并移除或替换占位。交接完成不等于缺口已解决。

占位计入遗留事项。含占位的 PRD 不得发布。

## 5.7 草稿提示

文首必须有与草稿类型一致的提示：

| `draft_kind` | 提示 |
| --- | --- |
| `risk_draft` | 本文档基于未就绪的需求分析生成，存在未解决的阻塞问题，仅供沟通，不得作为开发或测试依据。 |
| `conditional_draft` | 本文档存在待回答的问题和暂定假设，见“遗留事项”。 |
| `stale_draft` | 本文档基于已过期的分析结果生成，内容可能与最新需求不符。 |
| `formal_draft` | 草稿，待产品经理确认后发布。 |

正式发布后的版本不再带草稿提示。

# 六、编号、追溯与修改分流

## 6.1 正式编号

- 格式：`PRD-` 加分析前缀加三位序号，例如 `PRD-FR-001`、`PRD-BR-003`、`PRD-AC-012`。
- 分配范围：`GOAL`、`SCN`、`FR`、`BR`、`CON`、`NFR`、`AC`、`FLOW`、`STATE`、`BND`、`EXC`。
- 同一需求内唯一；一经分配不变、不复用、不重排；废止只改状态，不删除。
- 跨需求引用写成 `需求编号/PRD-FR-001`，例如 `REQ-2026-001/PRD-FR-001`。
- 遗留事项中的问题、假设、决策、矛盾、缺口沿用分析条目编号，不另行分配。
- 序号由脚本分配，计数器存放在 `prd-trace.json`。同一输入重复生成时，已有追溯关系的条目沿用原编号。

## 6.2 追溯

- 每个正式条目在 `prd-trace.json` 中记录 `analysis_refs`，格式为 `需求编号/分析条目编号`。
- 一个正式条目可以对应多个分析条目；分析条目被拆分时，可以对应多个正式条目，并在变更记录中说明。
- 每个正式条目记录 `source_digest`，用于判断生成依据是否变化。摘要必须覆盖所引用分析条目的完整引用、`content`、`tag`、`status`、`sources`、`related_ids`，以及其他实际用于生成该正式条目的字段；不能只比较正文和状态。
- 摘要使用 SHA-256；参与计算的对象键排序、忽略序列化空白，保留数组顺序。引用多个分析条目时，按完整分析引用排序后汇总，保证同一输入得到同一摘要。
- `source_digest` 的具体输入为按完整引用排序的对象数组，每个对象含 `analysis_ref` 和该引用对应的完整分析条目 `item`。序列化使用 UTF-8、对象键排序、紧凑分隔、不转义正常 Unicode 字符，拒绝非有限数值；数组内部顺序保留。摘要为 `sha256:` 加 64 位小写十六进制。`content_hash` 则计算 Markdown 文件原始字节，两者不得混用。
- 正式条目可选记录稳定的 `mapping_key`。同一需求内唯一，供编号补丁幂等定位；旧 `1.0` 追溯缺少该字段仍可读取，不据此重编号。编号补丁格式见 §9.11。
- `meta.section_source_digests` 为可选的生成时章节依据快照：稳定章节键到 SHA-256 摘要的映射，不含 `info`、`changes`。覆盖章节所用的完整分析集合、适用的缺口及辅助来源名称；对象键排序、紧凑 UTF-8、保留数组顺序，拒绝非有限值。首次或同步保存时由脚本计算；依据摘要未变的整章原始字节保持，正式条目仍独立保护。该字段不取代分析权威或自然语言审查。
- 旧追溯缺少章节摘要仍可读，不重编号。同步可显式提供 `--previous-analysis`，其需求身份和分析修订必须匹配原 PRD 基准，用于建立旧章节依据；没有旧摘要或可信旧分析时明确警告证据不足，须补旧分析或人工逐章核对，不宣称已自动证明整章最小化。辅助资料缺失仍依 §4.4 降级，不伪造旧依据。
- 功能需求和验收条件的表格带“分析来源”列。
- 无法追溯的内容不得出现在需求性章节。章节导语、术语解释等说明性文字除外，但不得引入新规则。

## 6.3 修改分流

| 修改类型 | 例子 | 处理 |
| --- | --- | --- |
| 内容性 | 增删需求点、改规则、改验收条件、改范围、改优先级 | 转回需求分析做更正、补充或撤销，再同步 |
| 排版性 | 措辞润色、格式、章节排版、错别字 | 直接处理 |
| 无法判断 | 措辞改动可能改变含义 | 按内容性处理，并向用户说明原因 |

- 排版性修改后，次版本号加 1，不改变追溯关系，记录事件 `layout_edit`。
- **手工修改检测**：读取 `prd.md` 时，将其摘要与 `prd-trace.json` 中的 `content_hash` 比较。不一致时比对差异：只有排版性变化的，更新摘要；出现内容性变化的，提示转回需求分析，并记录 `manual_edit_detected`。
- 用户坚持保留内容性手工修改的，对应条目标注【与分析不一致】并列入遗留事项，含此标注的 PRD 不得发布。
- 比较使用追溯中兼容选填的 `meta.content_baseline`：上次经统一保存的 Markdown 原文，UTF-8 编码后的原始字节摘要必须等于 `content_hash`，不归一化换行；它不是分析权威或发布快照。首稿、重复生成、同步和编辑成功时在同一事务中更新正文、摘要及基准。旧追溯无基准仍可读；当前正文与摘要一致时可在下一次合法保存建立基准。已修改的旧稿无基准时，必须补显式旧正文且摘要匹配，不能用重新生成结果猜旧稿或宣称已自动证明差异无害。
- 差异比较覆盖整份正文，包括非编号章节和未标记文本；语义分流由模型及人工核对，格式解析通过不证明含义相同。只读查看不写事件；显式记录检测时追加 `manual_edit_detected`，不递增版本、不将当前手改摘要重置为已处理，也不撤销用户原改动。实际收到坚持保留的回答后，保存标注及遗留项，首次发布前次版本递增一次，并在事件中说明处理。
- 不一致遗留项沿用 `prd:residual` 块：正式条目用完整 PRD 引用 `需求编号/PRD-FR-001` 等定位；非编号内容用 `需求编号/prd/sections/<section_key>` 定位对应内容章节，不指向 `info`、`changes` 或 `residuals`。原位置和遗留项均带【与分析不一致】，遗留项说明差异及回交分析建议；标注与定位须成对。
- 排版编辑及同输入重复生成不得抹去既有不一致。同步须核对分析确实覆盖该变化，不能仅凭修订递增、摘要一致或问题状态改变清除。编辑不前移分析基准，不用排版入口绕过待同步或分析门禁。
- 新增不一致遗留项后，原遗留章中独立的“无适用遗留项”等空集合提示已不再为真，保存时允许并移除此类提示；不能以此为由删改真实遗留说明或其他业务正文。

# 七、同步

## 7.1 触发

分析结果的 `meta.analysis_revision` 大于 `requirement.json` 中 `prd.based_on_analysis_revision` 时，PRD 为“待同步”。该状态由比较两个修订号得出，不单独存放。每次对 PRD 做操作之前，必须先检查。

## 7.2 同步步骤

1. 按 4.2 校验分析结果并判定草稿类型。
2. 按 6.2 重新计算 `source_digest` 并与已有值比对，把条目分为新增、修改、撤销、待重评、未变五类。仅标签、来源或关联关系变化也属于修改；可读取 `analysis-events.jsonl` 补充变更原因。
3. 只重写受影响条目对应的内容；未变条目一字不动，编号不变。
4. 新增条目分配新编号；撤销条目标为 `abolished`；待重评条目标为 `to_confirm`。
5. 按 9.5 核对缺口与接收问题的对应关系及关闭条件，更新缺口和占位；重新汇总遗留事项，重新判定草稿类型和草稿提示。
6. 生成变更摘要，写入变更记录和 `prd-events.jsonl`。
7. 更新 `requirement.json` 的 `prd` 块。

变更摘要包含：新增、修改、废止、待确认的条目编号，就绪度的变化，遗留事项的变化。

## 7.3 已发布版本的同步

已发布版本不被覆盖。同步生成新的工作稿，已发布的快照保持不变，现行基线仍是最新的已发布快照，直到新版本发布。

## 7.4 过期分析的同步

分析状态为 `stale` 时，同步结果为 `stale_draft`，不得提交评审或发布。

# 八、版本与发布

## 8.1 状态

| 状态 | 标识 | 说明 |
| --- | --- | --- |
| 草稿 | `draft` | 生成或同步后的默认状态 |
| 评审中 | `in_review` | 已提交产品经理评审 |
| 已发布 | `released` | 产品经理确认并发布，成为基线 |
| 已废弃 | `deprecated` | 需求整体不再做，保留全部文件 |

流转：`draft` → `in_review` → `released`；`in_review` 可以退回 `draft`；任何状态经产品经理明示可以转为 `deprecated`。`requirement.json` 的 `prd` 块描述当前工作稿，已发布基线以 `prd/versions/` 中最新的快照为准。

## 8.2 版本号

- 格式为 `主.次`。首次发布之前为 `0.N`，首次生成为 `0.1`，每次生成、同步或排版修改后 N 加 1。
- 首次发布为 `1.0`。
- 发布之后，内容性变更（经同步）主版本加 1，排版性修改次版本加 1。
- 发布之后的工作稿使用“下一个版本号加 `-draft`”，如 `2.0-draft`，发布时去掉后缀。

## 8.3 提交评审

`formal_draft` 和 `conditional_draft` 可以提交评审；`risk_draft` 和 `stale_draft` 不得提交评审。

## 8.4 发布条件

必须全部满足，否则拒绝发布并逐条说明：

1. 最新的分析校验结果为 `pass`，分析状态不是 `stale`。
2. 分析就绪度为 `ready_for_document`。
3. PRD 不处于待同步状态。
4. PRD 校验为 `pass`：没有占位，没有未关闭的缺口，没有【与分析不一致】。
5. 状态为 `in_review`。
6. 产品经理明示确认，记录确认人和时间。本 Skill 和分析 Skill 均不得代为确认。

## 8.5 发布动作

1. 状态改为 `released`，版本号定稿。
2. 写入只读快照 `prd/versions/prd-<version>.md` 及对应的追溯文件，记录摘要。
3. 记录事件 `release_confirmed` 和 `release`。`release` 事件的 `snapshots` 按 §9.6 登记两份快照路径及原始字节摘要，不另设发布清单。
4. 已发布 PRD 成为现行基线。新需求与它冲突时，由 Requirement Analyst 按基线变更规则处理，本 Skill 不做冲突分析，也不修改其他需求的 PRD。

## 8.6 已发布不可变

不得修改已发布的快照。需要修改时，经同步或内容变更产生新版本。快照摘要与记录不符时，校验失败。

## 8.7 废弃

产品经理明示后，状态改为 `deprecated`，保留全部文件，不再同步。分析侧撤销了全部条目时，本 Skill 只提示产品经理是否废弃，不自动废弃。

## 9.2 文件归属

| 位置 | 维护者 | 说明 |
| --- | --- | --- |
| `requirement.json` 的 `prd` 块 | 本 Skill | `common` 块不改 |
| `prd/prd.md` | 本 Skill | 用户的排版性修改经本 Skill 处理 |
| `prd/prd-trace.json` | 本 Skill | 不手工编辑 |
| `prd/prd-events.jsonl` | 本 Skill | 只追加，不修改 |

| `analysis/` | Requirement Analyst | 本 Skill 只读 |

信息只存放一处：PRD 版本、状态、基于的分析修订号只存放在 `prd` 块中，`prd.md` 的“文档信息”由脚本据此渲染，不手工维护。生成时的就绪度和草稿类型是 PRD 侧的快照，存放在 `prd-trace.json` 的 `meta` 中；当前的分析状态和就绪度不在本 Skill 的文件中存放，需要时读取 `analysis-result.json`。

## 9.3 prd.md 规范

- 文首依次为：草稿提示（如有）、文档信息、变更记录。
- 文档信息包含：需求编号、标题、PRD 版本、状态、草稿类型、基于的分析修订号、生成时间、未覆盖的分析项。
- 每个正式条目带正式编号；功能需求和验收条件用表格，含“分析来源”列。
- 标注格式见 5.3。
- 正文使用不可见 HTML 注释定位机器检查范围，不增加可见次要标签。块标记为 `<!-- prd:section <key> -->` / `<!-- /prd:section -->`、`<!-- prd:item <prd_id> -->` / `<!-- /prd:item -->`、`<!-- prd:gap <gap_id> -->` / `<!-- /prd:gap -->`、`<!-- prd:residual <reference> -->` / `<!-- /prd:residual -->`。章节可以包含其他块，其他块不得嵌套，重复、交叉和不成对标记均拒绝。
- 默认章节键依次为 `info`、`changes`、`background`、`scope`、`scenarios`、`functional_requirements`、`business_rules`、`flows_states`、`boundaries_exceptions`、`constraints`、`acceptance_criteria`、`ux`、`technical`、`impact`、`residuals`、`appendix`。模板可以调整中文标题和布局，但必须保留内容对应的稳定键及条目身份；文首仍为信息和变更记录。
- 正式编号和标注在其条目块内核对；表格的条目标记放在单元格内，不破坏表格结构。已废止编号仅在 `changes` 留痕，不作为有效条目。未关闭缺口的占位块含 `待分析补充`，每个请求只对应一个占位；其他章节使用引用说明，关闭后占位移除。
- 遗留项块以完整分析条目引用定位；无独立编号的待设计事项使用 `/ux_assessment/design_pending_items/<index>` JSON Pointer。问题及其假设、决策、推断和未处理矛盾缺口应当按 §5.5 分别可追溯，不能以别处出现编号充数。与分析不一致的 PRD 内容另按 §6.3 的完整 PRD 引用或稳定章节引用定位，不冒充分析条目。
- 文档信息由脚本渲染为可见键值表，包含 §9.3 所列字段；校验可见值与权威元数据一致。机器标记不代表语义忠实性已被自动证明，未标注的需求性文本和内容充分性仍须模型与人工评审。

## 9.4 追溯文件

文件：`prd-trace.json`。带版本号 `schema_version`，新增字段不得破坏已有文件的读取。

```json
{
  "schema_version": "1.0",
  "requirement_id": "REQ-2026-001",
  "meta": {
    "draft_kind": "conditional_draft",
    "generated_under_readiness": "conditionally_ready",
    "content_hash": "sha256:…",
    "counters": { "FR": 12, "BR": 5, "AC": 9 }
  },
  "items": [
    {
      "prd_id": "PRD-FR-003",
      "kind": "functional_requirement",
      "analysis_refs": ["REQ-2026-001/FR-3"],
      "tag": "inferred",
      "status": "active",
      "introduced_in": "0.1",
      "source_digest": "sha256:…"
    }
  ]
}
```

| 字段 | 说明 |
| --- | --- |
| `meta.draft_kind` | 草稿类型，见 4.2 |
| `meta.generated_under_readiness` | 生成时分析的就绪度 |
| `meta.content_hash` | `prd.md` 的内容摘要，用于手工修改检测 |
| `meta.content_baseline` | 兼容选填的上次统一保存正文；摘要一致性、旧稿兼容及显式旧正文见 §6.3 |
| `meta.counters` | 各类编号的已分配最大序号 |
| `meta.section_source_digests` | 可选生成时章节依据摘要；缺省旧追溯兼容与证据不足处理见 §6.2 |
| `items[].prd_id` | 正式编号，见 6.1 |
| `items[].kind` | 对应分析中的类别，如 `functional_requirement`、`business_rule`、`acceptance_criterion` |
| `items[].analysis_refs` | 对应的分析条目，格式 `需求编号/分析条目编号` |
| `items[].tag` | 继承分析标签；对应多个分析条目时取最不确定的一个（`assumption` 低于 `inferred` 低于 `confirmed`） |
| `items[].status` | `active`、`to_confirm`、`abolished` |
| `items[].introduced_in` | 引入时的 PRD 版本 |
| `items[].source_digest` | 生成依据的稳定摘要，覆盖字段及计算规则见 6.2 |

## 9.5 缺口回交文件

文件：`gap-requests.json`。顶层为对象，必含 `schema_version: "1.0"`、`requirement_id`、`counters: {"GAPREQ": N}` 和请求数组 `requests`。计数器为非负整数且不小于历史已分配最大序号，空集合计数器为 `0`；关闭的请求保留，不删除、不复用编号。封装和单条请求允许不改变已知语义的扩展字段，标记状态时须保留它们。

每个缺口含：`id`（`GAPREQ-N`，同一需求内唯一、不复用）、`needed_for`（需要这些信息的 PRD 章节）、`description`（缺什么）、`related_analysis_refs`（相关的分析条目，可为空）、`raised_in`（登记时的 PRD 版本）、`status`。

**引用格式**：`related_analysis_refs` 统一使用 `需求编号/分析条目编号`，如 `REQ-2026-001/FR-3`。分析侧转入问题的 `related_ids` 前必须校验并规范化：本需求引用转为 `FR-3`，跨需求引用保留完整格式；空数组保持为空，不臆造关联。

**稳定交接**：分析侧在“补充”时，为每个缺口登记一个接收问题，在该问题中记录 `gap_request_ref: "GAPREQ-N"`。该引用由分析侧维护，存放在 `analysis-result.json` 中，本 Skill 只读。同一缺口只对应一个接收问题；重复交接或中断重试时复用已有问题，不重复创建。分析侧必须先成功保存接收问题，再仅将缺口的 `status` 改为 `handed_over`，不修改缺口文件的其他内容；本 Skill 不写入 `analysis/`。

`status` 取值：

| 状态 | 含义与维护方式 |
| --- | --- |
| `open` | 待交接；本 Skill 登记，分析侧尚未完成登记确认 |
| `handed_over` | 接收问题已成功保存，由分析侧标记；不表示分析缺口已解决 |
| `closed` | 本 Skill 在同步中核对接收问题和实际分析内容，满足关闭条件后标记 |

**关闭条件**：本 Skill 通过问题的 `gap_request_ref` 找到对应关系后，必须同时满足以下两项，才能关闭缺口并移除或替换占位：

1. 接收问题不再为 `open`。
2. 分析结果已提供所需的有效内容，或已明确记录原内容不再需要的依据，原占位已不再适用。

仅登记问题、仅改变问题状态，或仅将缺口标为 `handed_over`，均不足以关闭缺口。采用暂定假设补足内容的，仍须按 5.3、5.5 保留标注和遗留事项；无法唯一找到接收问题时，保留缺口和占位并提示用户。

`closed` 请求另必含生成侧维护的 `resolution`：`kind` 为 `supplied` 或 `not_needed`，`analysis_refs` 为非空完整分析引用数组，`reason` 为依据说明。引用须存在、有效且有内容；`not_needed` 须引用说明不再需要的分析决策或范围依据，不接受只有生成器自述的关闭。校验器核对依据存在、状态及占位关系，不代替自然语言充分性评审。

`gap_request_ref` 是分析问题的选填扩展字段，取本需求内 `GAPREQ-N`；旧问题无此字段仍合法。同一缺口至多一个接收问题。`open` 可以尚未接收，也可以在保存后标记中断时已经有唯一问题；`handed_over` 和 `closed` 必须有唯一接收问题。跨需求资料仅由调用方显式提供，不隐式扫描工作区。

## 9.6 事件日志

文件：`prd-events.jsonl`，每行一个事件，只追加不修改。字段：`time`、`prd_version`、`change_type`、`summary`、`affected_prd_ids`、`based_on_analysis_revision`、`actor`（`user` 或 `prd_generator`）。发布确认事件另含 `confirmed_by`。

`change_type` 取值：`initial_generation` 首次生成；`sync` 同步；`layout_edit` 排版修改；`manual_edit_detected` 检测到手工修改；`gap_request` 缺口回交；`submit_review` 提交评审；`release_confirmed` 产品经理确认发布；`release` 发布；`deprecate` 废弃。

`release` 事件另必含 `snapshots` 对象，含 `prd` 和 `trace` 两项；每项含 `path` 和 `sha256`。路径相对于当前 `prd/`，必须分别为 `versions/prd-<prd_version>.md`、`versions/prd-trace-<prd_version>.json`；摘要为原始文件字节的 `sha256:` 加 64 位小写十六进制。不允许绝对路径、越界或符号链接。一个版本只能有一个发布事件；记录缺文件、文件缺记录、重复记录或摘要不符均失败。尚无发布时允许 `versions/` 不存在。该校验面向可信本地工作区的一致性，不认证遭同时篡改的日志和快照。

## 9.7 requirement.json 的 prd 块

```json
"prd": {
  "based_on_analysis_revision": 5,
  "status": "draft",
  "version": "0.3"
}
```

`status` 取值见 8.1。PRD 是否待同步由比较 `based_on_analysis_revision` 与当前分析修订号得出，不单独存放。

## 9.8 枚举值对照

| 字段 | 取值 |
| --- | --- |
| `prd.status` | `draft` 草稿；`in_review` 评审中；`released` 已发布；`deprecated` 已废弃 |
| `draft_kind` | `risk_draft` 风险草稿；`conditional_draft` 有条件草稿；`stale_draft` 过期草稿；`formal_draft` 正式草稿 |
| `items[].status` | `active` 有效；`to_confirm` 待确认；`abolished` 已废止 |
| `gap-requests[].status` | `open`、`handed_over`、`closed` |
| `items[].tag` | `confirmed`、`inferred`、`assumption`，与分析侧一致 |

## 9.9 校验规则

校验脚本（`validate_prd.py`）必须检查：

1. 追溯文件结构符合 `schemas/` 下的格式定义，必填字段齐全。
2. 正式编号唯一、不复用，计数器不小于已分配的最大序号。
3. 每个 `analysis_refs` 都存在于当前分析结果；指向 `withdrawn` 条目的，状态必须为 `abolished`。
4. 正文中的每个正式编号在追溯文件中存在；状态为 `active` 或 `to_confirm` 的条目都在正文中出现。
5. 标签为 `inferred` 或 `assumption` 的条目带【推断】或【暂定】；`to_confirm` 的条目带【待确认】。
6. `abolished` 的条目不出现在有效章节。
7. 草稿类型与草稿提示一致，并与分析当前状态一致：分析为 `stale` 时必须为 `stale_draft`。
8. 遗留事项章节覆盖 5.5 的全部应列项。
9. “待分析补充”占位与 `gap-requests.json` 中的缺口一一对应。
10. “文档信息”与 `prd` 块一致。
11. `versions/` 下快照的摘要与记录一致。
12. 缺口的 `related_analysis_refs` 格式符合 9.5；分析侧已登记的接收问题通过 `gap_request_ref` 唯一对应缺口；`closed` 的缺口满足 9.5 的关闭条件。未能找到接收问题的 `open` 缺口属于待处理，不据此判为结构失败。

**校验结果分三种**：通过 `pass`、警告 `warning`、失败 `fail`。警告情形：PRD 待同步；存在 `open` 的缺口；检测到手工修改但未处理；未发布工作稿含按 §6.3 成对标注的不一致内容，诊断必须定位目标并明确不得发布。不一致标注与遗留项不成对、目标不存在、正文基准摘要与 `content_hash` 不符，以及已发布产物含不一致标注，均为失败。其余违反上述规则的为失败。

**校验失败时**：脚本必须输出出错的条目编号和原因。模型据此修正后重新校验。校验通过之前，不得提交评审或发布，不得向用户宣布生成完成。连续修正 3 次仍失败时，停止修正，向用户说明问题，保持草稿状态。

校验器只读，诊断含 `rule`、`level`、`item_id`、`path`、`message`，无对应条目时以 `$` 定位。标准输出为包含 `status` 和 `diagnostics` 的单个 JSON；退出码 `pass=0`、`warning=1`、`fail=2`，失败优先且保留适用诊断。显式提供跨需求分析，不读取人用报告、不调用分析写入器。

仅有当前文件时不得宣称已证明历史编号未复用。可显式提供前一追溯，或读取已登记发布快照中的追溯，检查编号保留、计数器不回退、引入版本与既有稳定映射身份不被重置。待同步工作稿的旧来源摘要与当前分析不同应报告同步警告，而不是把该差异单独判为结构失败；独立格式错误仍失败，过期分析仍须遵守草稿类型规则。可选章节依据摘要存在时检查其结构；已同步稿与当前依据不符为失败，待同步差异不单独判结构失败。章节摘要及缺省旧格式处理见 §6.2；辅助来源不可读时只跳过依赖该来源名称的比较并明确降级。

## 9.10 多人协作

- 发布确认必须记录确认人和确认时间。
- 写入 `prd/` 前，校验 `prd` 块的版本和所依据的分析修订号：与读取时不一致，拒绝写入并提示重新读取，不覆盖他人的修改。
- 首次草稿、同一分析输入的重复生成，以及显式同步模式下的未发布工作稿增量，由 `write_draft.py` 统一编排保存。默认模式不执行同步；`--sync` 模式复用只读 `check_sync.py` 的差异结果，核对未变条目原始字节和编号，按 §7.2 定向更新，并按 §9.5 核实缺口关闭。编号映射补丁与候选正文、缺口材料分离，不改变 §9.11 的补丁协议；门禁、编号、信息渲染和 PRD 校验复用各自脚本。已发布版本另建工作稿的行为仍按 §7.3 实现，不通过首稿或本阶段未发布同步入口覆盖。
- 显式编辑同样由 `write_draft.py` 统一编排，只接纳已有未发布工作稿。输入绑定读时 PRD 版本、分析修订和正文摘要；排版保存、手工检测事件及用户坚持保留分别处理。旧正文、候选和用户坚持信息与编号补丁分离；`render_info.py`、`check_sync.py`、`validate_prd.py` 保持只读。正文基准与不一致规则见 §6.3；检测本身不授权修改需求或分析。
- 先构造并校验候选，再重新核对读时版本、分析修订及当前待写文件，拒绝覆盖并发修改；只保存本需求的正文、追溯、缺口、追加事件，以及 `requirement.json` 的 `prd` 块。不得创建需求或 `common`，不得改动其他块、分析文件和已发布快照。
- 校验失败保留候选并报告诊断；预期警告完整展示，过期分析仍须用户坚持后才生成。写入失败或中断不得报告为完整成功，恢复时重新核对当前输入。重复生成遵守 §8.2 的版本规则，正式编号、映射、来源摘要及需求正文保持稳定；文档信息和生成事件按版本更新。

## 9.11 编号映射补丁

编号补丁使用独立 `patch_version: "1.0"`，必含 `requirement_id`、`base_prd_version`、`base_analysis_revision` 和 `items`。首次无 `prd` 块时版本为 `null`，否则为读取时的版本字符串；分析修订为正整数。写入前任一读时版本不符即拒绝，不盲改数字重试。

每项必含非空 `mapping_key`、`kind`、非空且不重复的完整 `analysis_refs`；可选 `prd_id` 仅定位已分配条目，不能指定新编号。同一键重试沿用既有编号，一对多映射使用不同键，同一补丁键不重复。旧追溯无键时通过明确的既有 `prd_id` 定位；歧义或键与编号冲突则拒绝。未知字段、模型提交的计数器、摘要或业务正文均拒绝。实际分配及幂等写入由 `assign_ids.py` 负责，格式校验器不提前写入。

`kind` 与前缀依次对应：`goal/GOAL`、`scenario/SCN`、`functional_requirement/FR`、`business_rule/BR`、`constraint/CON`、`non_functional_requirement/NFR`、`acceptance_criterion/AC`、`flow/FLOW`、`state/STATE`、`boundary/BND`、`exception/EXC`。正式编号至少三位，不截断增长后的序号。

# 十、与 Requirement Analyst 的协作

本 Skill 与 Requirement Analyst 并列安装，各自独立，只通过共享工作区交换数据。分析侧规格的第十节是协作规则的另一半，两边必须一致。

## 10.1 分工

| 环节 | 负责方 |
| --- | --- |
| 创建需求目录、分配需求编号 | Requirement Analyst |
| 理解、分析、追问、收敛、变更影响 | Requirement Analyst |
| 校验分析结果并判定可生成的草稿类型 | 本 Skill 调用分析侧的校验脚本 |
| 生成 PRD、正式编号、追溯 | 本 Skill |
| 登记新问题、更正、撤销 | Requirement Analyst |
| 同步、版本、发布 | 本 Skill |

## 10.2 协作流程

1. 用户要求生成 PRD。本 Skill 按 4.2 检查：没有分析结果的，转入需求分析。
2. 分析结果可用时，生成对应类型的草稿，列出遗留事项。
3. 生成中发现分析缺口的，占位并登记缺口，建议用户转入需求分析。
4. 分析 Skill 处理缺口、答复或需求变化后，分析修订号增加，PRD 变为“待同步”，本 Skill 重新读取并同步。缺口按问题的 `gap_request_ref` 追溯，满足 9.5 的关闭条件后才关闭，不把 `handed_over` 当作已解决。
5. 用户要改需求内容的，转回需求分析，不在 PRD 中直接改。
6. 分析就绪度为 `ready_for_document` 且 PRD 满足发布条件时，产品经理确认后发布。

## 10.3 本 Skill 必须遵守的交接约束

- 只读 `analysis-result.json`，不读 `analysis-report.md`；`analysis-events.jsonl` 和 `source-manifest.json` 只读，仅用于补充说明。
- 保留标签语义：推断和假设在 PRD 中保留标注，暂定假设在 PRD 中列为待验证。
- 状态决定去留：`withdrawn` 的条目不进入 PRD，`to_reassess` 的条目不写成确定内容。
- 编号各管各的：正式编号由本 Skill 分配，分析条目编号不直接作为正式编号，每个正式条目都记录对应的分析条目。
- 生成过程中不得修改 `analysis/` 下的任何文件，也不调用会写入 `analysis/` 的脚本。

## 10.4 工作区共享约定

`requirement.json` 分块维护，各 Skill 只改自己的块：

| 块 | 内容 | 维护者 |
| --- | --- | --- |
| `common` | `requirement_id`、`title`、`project_id`、`created_at` | 创建时由分析侧写入，用户可改标题 |
| `prd` | `based_on_analysis_revision`、`status`、`version` | 本 Skill |

分析状态、就绪度、分析修订号不在 `requirement.json` 中存放，需要时读取 `analysis-result.json` 的 `meta`。

## 10.5 已发布 PRD 与历史需求

已发布的 PRD 是 Requirement Analyst 的历史需求资料。分析侧可只读各需求 `prd/versions/` 下的已发布快照及对应追溯文件，用于历史对照和编号追溯；当前工作稿 `prd/prd.md` 不作为现行基线。分析侧对 `prd/` 的唯一写入例外是按 9.5 标记缺口 `status` 为 `handed_over`。

本 Skill 只保证 `prd/versions/` 下的快照和元数据符合约定，不做历史需求检索和冲突分析。分析结果中 `impact_analysis` 的内容只作为“关联与影响”写入，并标明是分析建议，不据此修改其他需求的 PRD。

# 十一、Skill 文件结构与配置

## 11.1 目录结构

Skill 名只能用小写字母、数字和连字符，目录名必须与 Skill 名一致，入口文件名固定为 `SKILL.md`。

```text
prd-generator/
├── SKILL.md                         入口，只写流程和硬规则，控制在约 120 行内
├── references/                      按需读取
│   ├── gating-rules.md              生成前检查、草稿类型、降级规则
│   ├── generation-rules.md          内容映射、标注保留、状态去留、遗留事项
│   ├── numbering-and-trace.md       正式编号、追溯、修改分流
│   ├── sync-rules.md                同步步骤、变更摘要、已发布版本的同步
│   ├── versioning-and-release.md    状态、版本号、评审、发布条件
│   └── prd-structure.md             默认章节、模板适配
├── schemas/
│   ├── prd-trace.schema.json
│   ├── gap-request.schema.json
│   └── numbering-patch.schema.json
├── templates/
│   ├── prd.md
│   └── change-summary.md
└── scripts/
    ├── check_gate.py                调用分析侧校验，判定草稿类型或拒绝
    ├── assign_ids.py                分配正式编号，维护追溯文件和计数器
    ├── check_sync.py                比较修订号和摘要，列出受影响条目
    ├── render_info.py               渲染文档信息，计算内容摘要
    ├── write_draft.py               编排首稿、显式同步或编辑的候选校验、并发检查及保存
    ├── validate_prd.py              执行 9.9 的全部检查
    └── snapshot_release.py          写入发布快照并记录摘要
```

参考文件、格式定义和脚本按能力划分，可以按实际启用的能力取舍。

## 11.2 配置要点

- 入口文件的 `description` 写清触发场景：生成 PRD、需求文档、同步 PRD、提交评审、发布版本、查看遗留事项。
- 本 Skill 是面向用户的入口，应当允许用户直接调用，同时允许 Claude 在需求文档场景自动调用。
- **不使用 `context: fork` **：本 Skill 需要利用当前对话中的信息，独立上下文会丢失。
- 依赖 Requirement Analyst 的校验脚本，两个 Skill 必须一同安装。
- 细则放在 `references/` 中渐进加载，入口文件不堆砌规则；新增规则优先放入参考文件，每新增一项能力，应当有对应的回归场景。

## 11.3 脚本职责

- ** `check_gate.py` **：只调用分析侧的 `validate_analysis.py`，不调用任何会写入 `analysis/` 的脚本。
- ** `assign_ids.py` **：模型只提交“哪些分析条目对应哪些正式条目”的补丁，编号由脚本分配，避免模型自行编号导致漂移或复用。
- ** `check_sync.py` **：只做比对，不改写文件。
- ** `render_info.py` **：根据权威元数据渲染文档信息，计算正文原始字节摘要，不承担整份草稿保存。
- ** `write_draft.py` **：复用各确定性脚本，按 §9.10 保存首次草稿、同一分析输入的重复生成，或显式同步模式下的未发布工作稿增量及经 §9.5 核实的缺口关闭；显式编辑模式按 §6.3 保存经语义核对的排版候选、记录手工检测，或在用户坚持后保存不一致标注及遗留项。编辑分流由模型完成，脚本不声称自动证明含义相同；不改变分析基准、编号身份、缺口内容或交接进度。共用候选校验、并发检查和中断恢复机制；更新正文比较基准，不以交接或状态变化自动关闭缺口。自然语言补足是否充分仍由模型及人工评审。只写未发布工作稿，不承担评审、发布或发布后另建工作稿；不扩大编号补丁接口。
- ** `validate_prd.py` **：校验通过之前，不得更新 `prd` 块的状态为 `in_review` 或 `released`。
- ** `snapshot_release.py` **：只在发布条件全部满足且有确认记录时运行。

| PG-17 | 用户要求修改需求内容 | 转回需求分析，不在 PRD 中直接改 | 修改分流 |
| PG-18 | 用户只润色措辞和排版 | 直接处理，次版本加 1，需求含义不变 | 修改分流 |
| PG-19 | PRD 被手工改了需求内容 | 检测到并提示转回分析；坚持保留则标【与分析不一致】且不得发布 | 修改分流 |
| PG-20 | 不依赖界面的需求，以及依赖界面但无视觉资料的需求 | 前者不生成界面章节，后者列为待设计事项 | 降级规则 |
| PG-21 | 技术评估缺省 | 不写技术结论，只列研发确认项 | 降级规则 |
| PG-22 | 发布条件逐项不满足 | 拒绝发布并逐条说明 | 发布条件 |
| PG-23 | 产品经理确认发布 | 记录确认人和时间，生成只读快照 | 发布 |
| PG-24 | 发布之后分析发生变化 | 生成新的工作稿，旧快照不动，现行基线仍是旧版本 | 同步、版本 |
| PG-25 | 已发布快照被改动 | 校验失败 | 校验 |
| PG-26 | 同一输入重复生成 | 编号和内容保持稳定 | 编号与追溯 |
| PG-27 | 生成和同步的全过程 | 没有修改 `analysis/` 下的任何文件 | 协作 |
| PG-28 | 多人同时写入 | 版本不一致时拒绝写入 | 多人协作 |
| PG-29 | 缺口交给分析 | 缺口引用使用完整格式，接收问题以 `gap_request_ref` 唯一对应缺口；交接中断重试不重复登记问题 | 缺口回交、协作 |
| PG-30 | 缺口已为 `handed_over`，或问题已改变状态但所需内容仍未补足 | 保留缺口和占位，不误判为已解决，不允许发布 | 缺口回交、发布条件 |
| PG-31 | 缺口所需内容已补足，或有依据明确不再需要 | 按接收问题与实际内容核对后关闭，移除或替换占位；暂定假设仍保留标注和遗留事项 | 缺口回交、同步 |
| PG-32 | 分析条目只改变标签、来源或关联关系 | 摘要变化，更新受影响内容及标注或关联，正式编号保持稳定 | 同步、标注保留 |
| PG-33 | 核心完成清单满足，仅剩非阻塞研发确认项 | 分析为 `ready_for_document` 且校验通过时可生成正式草稿；发布仍逐项核对条件，不因该确认项单独拒绝 | 门禁检查、发布条件 |
| PG-34 | 生成依据的对象键顺序或 JSON 排版变化 | 稳定序列化后的摘要不变，不触发条目重写 | 同步最小化 |

## 12.2 评价指标

1. 追溯完整率：需求性条目中有对应分析条目的比例，目标为全部。
2. 标注保留率：分析中的推断、假设、待重评条目，在 PRD 中保留标注的比例。
3. 状态去留正确率：已撤销条目未进入 PRD 的比例。
4. 同步最小化：同步时受影响条目之外被改动的内容数量。
5. 编号稳定率：同步前后已有编号未变化的比例。
6. 缺口回交准确率：被登记的缺口中确为分析缺失的比例，以及未登记而自行补全的数量。
7. 修改分流准确率：内容性与排版性修改被正确分流的比例。
8. 误发布次数：不满足发布条件而被发布的次数，目标为 0。

## 12.3 参考答案

每个场景保存人工评审的参考答案，包括期望的草稿类型、PRD 关键片段和追溯文件片段，不能仅用另一个模型给自己的生成结果打分。建议与分析侧共用样例：“高低压开关组合逻辑设计表”需求及其已有的各版解读作为第一组，“仿真任务管理优化”作为第二组。指标阈值在首轮评审后确定，不预先拍数。

# 附录一：术语

| 术语 | 含义 |
| --- | --- |
| 基线 | 已发布、现行有效的需求集合；本 Skill 中指 `prd/versions/` 下最新的快照 |
| 草稿类型（`draft_kind`） | 由分析的就绪度和状态决定的 PRD 草稿等级，见 4.2 |
| 正式编号 | 本 Skill 为 PRD 条目分配的 `PRD-` 前缀编号 |
| 追溯 | 正式条目与分析条目之间的对应关系 |
| 待同步 | PRD 基于的分析修订号低于当前分析修订号 |
| 缺口回交 | 生成时发现分析缺失，登记后交回需求分析处理 |
| 内容性修改 | 会改变需求含义的修改，必须回到需求分析 |
| 排版性修改 | 不改变需求含义的措辞、格式、排版修改 |
| 快照 | 发布时写入、之后只读的 PRD 版本文件 |
| 降级 | 前提资料缺失时，对应能力改为更保守的做法，并在文档中注明 |
