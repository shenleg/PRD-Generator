# PRD Generator：分阶段执行文档

本文档把完整规格转为开发、验证和人工评审的执行顺序；它不是实现完成或验收通过的记录。

## 如何使用本文档

- **依据**：[需求文档生成完整规格](spec.md)，下称“生成规格”；[需求分析完整规格](../requirement-analyst/spec.md)，下称“分析规格”；[分阶段执行文档写作规范](../shared/staged-execution-guide.md)。引用形式为“生成规格 §9.5”。
- **已确认的划分**：阶段 0～7 均为核心阶段，详细展开。阶段 3 是首次草稿的中间试用点；完整核心里程碑包含评审、发布、不可变基线、正式双 Skill 联调和真实试用。
- **已确认的配套工作**：新增交接协议作为首个分析侧配套补丁，安排在阶段 2；阶段 1 先固定格式和校验依据，阶段 0 不写产品代码。
- **退出条件是门禁**：未满足就不宣布本阶段完成，也不进入依赖它的下一阶段。程序校验通过不等于语义正确，草稿生成不等于发布批准。
- **场景唯一归属**：每个 `PG-xx` 只有一个首次完整验收阶段。此前可以验证局部条件，但不把局部结果记为整个场景通过；之后重复执行属于回归，不重复计算覆盖。
- **先改规格**：发现字段、状态或接口不够用，先形成问题和建议，获得确认并回写相关规格，再调整本计划和实现。本文不替规格定义新协议。
- **人工决定**：格式评审、参考要点认可、真实试用评价和发布确认由用户或指定负责人完成；AI 可以辅助整理，不能代签。

## 通用约定

### 开发仓库结构

沿用现有仓库，不另建重复的分析侧源码。维护文档、测试代码及场景、夹具、参考要点已按 Skill 分类，布局依据见 `docs/shared/repository-layout.md`；既有原文和认可正文保持原字节，封存证据中的旧路径及指纹不改写。以下目录组织不是新增产品接口。

```text
skill/
├── requirement-analyst/              既有分析 Skill，阶段 2 做配套修改
└── prd-generator/                    新生成 Skill，内部结构见生成规格 §11.1
tests/
├── requirement-analyst/              分析测试、辅助模块和重放驱动
├── prd-generator/                    生成测试、辅助模块和格式重放驱动
├── fixtures/prd-generator/           分析输入、文档夹具、反例和模板样例
├── scenarios/prd-generator/          每个 PG 场景的剧本
├── expected/prd-generator/           人工编写或修订并认可的参考要点
├── results/prd-generator/            分阶段运行、格式评审及人工验收记录
└── test_all.py                      统一发现两组测试，兼容原测试命令
workspace-sandbox/
└── prd-generator/                    独立试用工作区和保留证据
```

- 产品只安装两个 Skill 的生产目录；`tests/`、最小消费者和 `workspace-sandbox/` 不随 Skill 安装。
- 正式工作区沿用生成规格 §9.1。由分析侧创建需求目录和 `common`；生成侧不能为绕过前置条件自行创建需求。
- 已保存的历史模型输出、分析样例和最小消费者证据保持原样。新试跑使用新目录，不覆盖旧证据。
- `tools/minimal_prd_consumer.py` 仅供理解旧交接链路，不升级为正式生成器，也不将其整数版本协议冒充正式 PRD 版本协议。

### 每个阶段的工作循环

1. **写剧本**：在 `tests/scenarios/prd-generator/` 准备本阶段场景及可执行检查，列出输入、实际提问分支和文件归属断言。
2. **准备参考要点**：由人工编写或修订并认可 `tests/expected/prd-generator/` 中的预期草稿类型、关键文段和结构化片段。模型只辅助找遗漏。
3. **写最小实现**：只实现本阶段内容；协议变化先改规格。模型负责表达和语义判断，脚本负责确定性编号、摘要、门禁及校验。
4. **运行并留证**：保存实际输入、对话、候选补丁、脚本响应、最终文件和必要指纹。没有执行的步骤不写成已完成。
5. **分类修正**：按下表改对应模块，不把所有规则堆进 `SKILL.md`。
6. **回归并评审**：重跑此前已验收场景及受影响的分析侧测试；记录失败、跳过及限制，再判断退出条件。

| 失败类型 | 修改位置 |
| --- | --- |
| 门禁或草稿类型错误 | `gating-rules.md`、`check_gate.py` |
| 漏映射、标注丢失、遗留事项遗漏 | `generation-rules.md`、`prd-structure.md`、`templates/prd.md` |
| 格式不合法或诊断不准确 | `schemas/`、`validate_prd.py` |
| 正式编号或摘要漂移 | `assign_ids.py`、`numbering-and-trace.md` |
| 同步范围扩大、缺口误关闭 | `check_sync.py`、`sync-rules.md` |
| 分析侧重复登记或越权写入 | 分析侧 `update_analysis.py`、问题 Schema、`incremental-update.md` |
| 修改分流错误、手工改动漏检 | `numbering-and-trace.md`、`render_info.py`、`validate_prd.py` |
| 版本、确认、快照或发布错误 | `versioning-and-release.md`、`snapshot_release.py` |
| 不触发、丢会话信息、加载过多 | `SKILL.md` 及安装配置；保留生成规格 §11.2 的调用约束 |

文件定位不扩大脚本职责；若必须增加生产入口或改变文件归属，先补规格并评审。

### 场景剧本和运行记录

- 每个场景一份 `PG-xx.md`：场景说明、验证能力、输入、前置状态、分轮用户回答、参考要点、执行方式、预期文件变化及不应变化的文件。
- 预设回答只在实际问到对应问题后提供，不提前交给被测模型；参考答案与模型输入分离。
- 每次运行至少记录：日期、阶段、场景编号、结果（`pass`、`partial`、`fail`）、执行方式、源码版本、证据路径、适用指标和备注。
- 单独保存程序执行状态 `pass`、`warning`、`fail`，不得把脚本 `warning` 自动转换为场景失败，也不得仅因写出了文件就判场景通过。
- 区分静态检查、程序夹具测试、CLI 重放、实际模型调用、安装自动触发和人工评审。历史证据不冒充当前版本的新模型调用。
- 语义条件不能只靠字符串命中判定；尤其是忠实性、措辞不改含义、缺口是否真的补足，要由人工参考要点核对。

### 评价指标记录

依据生成规格 §12.2、§12.3记录下列指标。保留场景级原始计数、样本范围和统计口径；没有适用样本时记为不适用，不记作满分。

| 指标 | 记录内容 | 验收使用方式 |
| --- | --- | --- |
| 追溯完整率 | 需求性条目总数、有有效分析引用的数量 | 沿用规格“全部”的目标 |
| 标注保留率 | 各类需标注条目总数、正确保留数量 | 首轮人工评审后确定阈值；此前只记录 |
| 状态去留正确率 | 已撤销条目总数、未进入有效章节的数量 | 首轮人工评审后确定阈值；不得据此放宽状态硬规则 |
| 同步最小化 | 受影响范围及范围外内容改动数量 | 记录实测值，按规格 §7.2 检查未变条目一字不动 |
| 编号稳定率 | 既有正式编号总数、同步后未变数量 | 记录实测值，按规格 §6.1 检查编号不变、不复用 |
| 缺口回交准确率 | 登记缺口、确认确属缺失、未登记而自行补全的数量 | 首轮人工评审后确定阈值；不得自行补事实 |
| 修改分流准确率 | 内容性及排版性样本、正确分流数量 | 首轮人工评审后确定阈值 |
| 误发布次数 | 不满足发布条件而发布的次数及原因 | 沿用规格目标 `0` |

尚未确定的指标阈值只记录，不设阈值，不宣布全部量化达标。已有硬规则和规格目标继续生效。

### 写入、修正与版本管理

- 每次写入前核对读取时的 `prd.version` 和分析修订号，冲突则拒绝并重新读取；不盲改版本数字重试。依据生成规格 §9.10。
- 生成侧只读 `analysis/`。需要补充分析时，交还分析 Skill；生成 Skill 本身不能调用会写入 `analysis/` 的脚本。依据生成规格 §10.3。
- 分析侧唯一的 `prd/` 写入例外是缺口接收成功后将对应 `status` 标为 `handed_over`，不改缺口其他内容、不直接关闭缺口。依据生成规格 §9.5、§10.5。
- 连续修正 `3` 次校验仍失败，停止修正、保留草稿并报告问题。校验通过前不宣布生成完成、不提交评审或发布。依据生成规格 §9.9。
- 每个阶段独立分支开发；通过退出条件后先展示变更摘要，再由用户明确授权提交、合并及阶段标签。本文不构成自动提交、推送或打标签授权。
- 固定评审点：阶段 1 格式评审；每阶段结束前回归；阶段 3 后草稿试用；阶段 7 真实试用及最终评审。
- 删除、密钥及环境配置、CI/CD、推送、生产部署等操作仍须遵守用户单独授权要求。测试中的模拟发布确认不等于真实发布授权。

## 阶段 0：准备

**目标**：准备可评审材料和执行约束，不编写产品代码。

**对应规格**：生成规格 §2、§9、§10、§11、§12.1～§12.3；分析规格 §10。

**步骤**

1. **登记现状**：在 `tests/results/prd-generator/stage-0.md` 记录两份规格版本、分析 Skill 版本、既有回归结果及正式生成器尚未实现的事实。最小消费者通过不等于正式联调通过。
2. **整理样例**：在 `tests/fixtures/prd-generator/` 登记两组样例的原文、所采用的分析修订及来源。建议沿用规格 §12.3 的两组需求；不把旧分析报告当权威输入，不覆盖历史夹具。
3. **准备人工参考要点**：由人工编写或修订并认可 `tests/expected/prd-generator/`，明确预期草稿类型、必要文段、追溯片段、不确定性和禁止引入的规则。已有分析侧参考要点不能直接等同生成侧参考答案。
4. **建立场景目录**：在 `tests/scenarios/prd-generator/` 登记全部 `PG-01`～`PG-34` 的剧本索引；按总览指定唯一验收阶段。后续阶段实施前补齐该阶段剧本及人工参考要点。
5. **确认待定事项**：在下表记录人工结论和日期；需后续实测才能决定的事项，先确定决策责任、评审时点和未决期间处理方式，不伪造最终阈值。
6. **核对准备结果**：运行既有分析回归，保存原始输出；人工检查样例和待定事项后，形成阶段退出记录。

**退出条件**

- 两组样例的选取、分析输入来源和生成侧人工参考要点已获认可，证据在 `tests/results/prd-generator/stage-0.md`。
- 全部场景有唯一阶段归属，已准备阶段 1 的合法夹具计划和反例计划。
- 待定表各项已有明确结论；后续评审事项的责任、时点及未决处理已确定，但不把尚未发生的评审记作完成。
- 既有分析回归实际运行并保存结果；若不通过，先定位影响，不能把失败留给下游掩盖。
- 本阶段没有产品代码变更；没有改动旧证据。

**步骤**

1. **准备生命周期剧本**：为每个发布条件分别准备不满足和全部满足的输入，覆盖四类草稿、占位、未关闭缺口、待同步、手工内容不一致、非阻塞研发事项和废弃分支。
2. **实现状态与版本**：编写 `references/versioning-and-release.md`，实现草稿、评审、退回、发布和明示废弃；严格按规格 §8.2 分配发布前、发布后和工作稿版本。不能确定的版本交错示例先请用户裁定并补规格，不另造计数规则。
3. **实现发布前检查**：重新读取分析、校验 PRD、核对同步状态及 `in_review` 状态；逐项给出拒绝原因。`conditional_draft` 可评审但不得发布，非阻塞研发确认项不单独阻断满足条件的正式草稿。
4. **实现确认与快照**：编写 `scripts/snapshot_release.py`，仅在门禁全部满足且产品经理明示确认记录有效时定稿，保存 `versions/` 下文档、对应追溯文件和阶段 1 固定的摘要记录，追加确认及发布事件。
5. **实现发布后维护**：内容变化经分析同步创建新工作稿，排版变化按版本规则处理；不覆盖旧快照，现行基线保持为最新已发布快照，直到新版本正式发布。明示废弃保留全部文件并停止同步，不因分析条目全撤销而自动废弃。
6. **核实不变性及失败分支**：实际篡改测试快照后运行校验，确认失败；发布前检查后发生版本冲突要拒写。测试合成确认、真实人工确认和公开发布授权分别记载。
7. **补齐完整场景并回归**：用真实生成、同步和发布脚本链路替代阶段 1 的孤立快照夹具验证；保留夹具作为回归，不把合成发布称为产品发布。重跑此前场景及分析测试。

**退出条件**

- `PG-04`～`PG-05`、`PG-12`、`PG-19`、`PG-22`～`PG-25`、`PG-30`、`PG-33` 完整通过。
- 发布条件分别不满足时均拒绝且有具体原因；`handed_over` 或问题状态已变但内容不足仍阻止发布。
- 满足条件时有确认人和时间、定稿版本、对应快照及摘要；没有明示确认时不发布。
- 发布后同步产生新工作稿，旧快照和基线保持；篡改快照能被校验检出。
- 评审退回、明示废弃、不自动废弃及发布后排版版本变化有可复现补充检查；这些检查不另造 `PG` 编号。
- 此前全部场景和分析回归仍通过；未执行真实发布的事实如实记录。

**不做**：不代产品经理确认，不公开发布或生产部署，不修改其他需求的基线；安装后全链联调和真实需求试用属于阶段 7。

## 阶段 7：正式双 Skill 联调与真实试用

**目标**：验证实际安装的两个 Skill 能按文件归属完成全链路，并获得真实试用反馈。

**对应规格**：生成规格 §9.10、§10、§11.2、§12；分析规格 §10。

**实施状态**：正式双 Skill 联调、真实试用的首稿与实际内容变更同步、最终全量回归均已完成并留证。用户于 `2026-11-18` 明确通过最终人工验收，阶段 7 已退出。详见[阶段记录](../../tests/results/prd-generator/stage-7.md)及[最终验收报告](../../tests/results/prd-generator/final-acceptance.md)。

**步骤**

1. **安装正式目录**：按生成规格 §11.2 并列安装两个 Skill，编写或更新安装说明，核对依赖、入口调用、自动触发和当前会话承接；不把测试、消费者或沙盒装入产品。
2. **执行正式交接**：由生成 Skill 实际登记缺口，切回分析 Skill 接收和补充，再由生成 Skill 同步并核实关闭。替换阶段 2 的缺口替身，不让生成 Skill 越权调用分析写入脚本。
3. **核对全过程归属**：执行 `PG-27`，对生成和同步前后 `analysis/` 全部业务文件作指纹比较；分析侧补充造成的合法变化单独分段记录，不能混入生成侧只读断言。
4. **执行并发冲突**：执行 `PG-28`，覆盖分析修订变化、PRD 版本变化及缺口交接期间的交错写入；实际验证拒写和重新读取，不只检查错误文案。
5. **进行真实需求试用**：使用阶段 0 约定的真实需求与负责人完成生成、查看遗留事项、内容变更回交和同步；实际发布只有在产品经理另行明示确认后执行。没有真实发布授权时，可以用合成生命周期测试验证发布功能，并明确真实发布未执行。
6. **评审语义和指标**：由人工核对忠实性、标注、追溯、缺口准确性和修改分流，记录规格 §12.2 全部适用指标；尚无阈值的指标不扩称量化达标。
7. **完成最终回归**：重跑 `PG-01`～`PG-34`、补充边界检查及全部分析侧回归，输出 `tests/results/prd-generator/final-acceptance.md`，列出通过、失败、未执行及剩余事项。

**退出条件**

- `PG-27`～`PG-28` 完整通过，文件归属和冲突拒写都有实际证据。
- 正式两个 Skill 已实际联调，阶段 2 的替身限制已解除；实际自动触发与直接调用分别有记录。
- 全部 `PG` 场景及此前检查仍通过，分析侧回归无未解释失败。
- 真实需求已试用并有人工评审；未具备真实资料时本阶段保持未完成，不能自行用模拟案例替代。变更该退出条件须由用户明确批准并更新计划。
- 最终报告区分程序回归、模型行为、真实试用、人工确认和实际发布；未批准或未执行的发布不冒充完成。

**不做**：不追加高保真设计、技术设计、历史需求检索、跨需求冲突裁决、迁移或公开部署；这些不因联调而自动进入范围。

## 扩展阶段

本次不虚设扩展阶段。用户已选择完整生命周期作为核心；生成规格没有要求新增资料解析、历史检索或高保真制作能力，本文不据此增加开发范围。

生成规格 §4.4 的可选分析内容在核心映射中按资料降级处理，不是延期实现。若后续明确新增或延期某项能力，先更新规格和阶段划分，再仅按“进入条件、主要工作、退出条件”编写扩展阶段；前提不满足时不启动。

## 风险与应对

| 风险 | 应对 |
| --- | --- |
| 格式缺项由实现自行补齐，两侧读写分歧 | 阶段 1 先形成草案并回写规格，安排读取方及人工格式评审 |
| 旧分析回归通过被误认为新交接协议已实现 | 阶段 2 独立验证 `PG-29`，分析旧回归与新协议证据分开记录 |
| 重试造成重复问题，或先标记后保存 | 用 `gap_request_ref` 查重，实际验证失败和中断恢复，先保存再标记 |
| `handed_over` 被误当解决 | 同时核对问题状态与实际内容，阶段 4 检查保留，阶段 6 检查拒绝发布 |
| 同步只比较正文，漏掉标签、来源和关联 | 摘要覆盖全部实际生成字段，运行 `PG-32`、`PG-34` |
| 模型整篇改写导致未变内容漂移 | `check_sync.py` 只读定位，保留未变条目字节，按差异和指纹验收 |
| 校验器只能检查结构，却被当成语义评审 | 人工认可参考要点，保留实际模型输出，单独检查忠实性及缺口充分性 |
| 入口膨胀、失去会话信息 | 入口约 `120` 行内，细则按需加载，不使用 `context: fork` |
| 只用单一样例或参考答案泄漏 | 沿用不同类型的两组样例，参考要点与模型输入隔离，真实需求另作试用 |
| 最小消费者格式污染正式版本协议 | 保留旧证据，首批不静默迁移，正式版本依据生成规格 §8.2 |
| 并发检查与实际写入脱节 | 写入前复核分析修订号和 PRD 版本，正式联调加入交错写入测试 |
| 发布缺少确认、旧快照被覆盖 | 门禁与确认记录同时满足才发布，快照摘要校验，变更另建工作稿 |
| 已实现脚本被误报为安装及真实试用完成 | 阶段 7 单独运行直接调用、自动触发、正式交接和人工试用 |
| 未定阈值被自行补数或反过来放宽硬规则 | 未定阈值只记录；规格已有的追溯、编号、不变性和误发布目标仍生效 |
